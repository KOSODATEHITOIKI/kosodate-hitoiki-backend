# 権限表

更新日：2026-09-29。Issue #9として[バックエンド設計](バックエンド設計.md)2節の権限境界を、リソース×操作×利用者区分の表へ具体化したもの。実装はRLSポリシーとEdge Functions双方で、ここに記載した境界を守る（RLSだけに頼らずEdge Function側でも権限・状態を再確認する。[バックエンド設計](バックエンド設計.md)1・4節）。

利用者区分：

- **未ログイン**：認証なしでAPIを呼ぶ利用者
- **本人**：操作対象の所有者・作成者
- **他人**：ログイン済みだが対象の所有者ではない利用者
- **運営者**：運営アカウント（二段階認証必須）

凡例：`○`＝可、`×`＝不可、`△`＝条件付き（備考参照）

## 設計上の注意

- 「本人のみ」はRLSの`auth.uid() = user_id`（または該当カラム）判定を基本とし、Edge Function内でも同じ判定を行う（クライアントからの自己申告に依存しない。[バックエンド設計](バックエンド設計.md)1節）。
- 運営者判定は、`admin_users`テーブル（クライアントから書き込めない）への登録**と**、二段階認証済み（`aal2`）のセッションで行い、一般利用者のロール偽装を防ぐ。DBの`is_admin()`が両方を確認するため、直接RESTでも、二段階認証前の運営者には運営向けの情報が何も見えない。Edge Functionの`moderation`も`aal2`を必須とし、運営者でない人には機能の存在を明かさない（`404`を返す）。詳細は[運営の二段階認証](運営の二段階認証.md)。
- ブロック関係がある場合、他人からの投稿・コメント・共感の取得/作成は拒否する。**通報は、安全のため妨げない**（通報は運営へ届くもので、相手には届かない）。ブロックを示す拒否理由は返さない（相手に知らせない）。ブロック判定は各操作の権限チェックに横断的に適用する（[スキーマ定義](スキーマ定義.md)5節）。
- 利用停止中（`account_restrictions`が現在有効）の利用者は、対象が自分の既存投稿・コメントの参照を除く新規作成系操作をすべて拒否する。
