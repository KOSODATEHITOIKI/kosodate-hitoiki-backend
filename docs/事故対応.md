# 事故対応（侵入・漏えいの疑いがあるとき）

更新日：2026-10-23。**設計案**（採用は、運営の確認のあと）。侵入・不正アクセス・鍵の漏れ・データの漏えいが「起きたかもしれない」と気づいたときの、**検知 → 止める → 調べる → 直す → 報告する**の手順。判断に迷ったら、**先に止める**（止めたあとで、元に戻せる）。

> **法律の部分（5節）は、公式の情報を読んで、まとめたもの**だが、書いた者は、法律の専門家ではない。リリース前に、専門家（弁護士など）に確認して、手順を確定する（調査の詳細は、[法的対応](法的対応.md)）。

## 1. 気づくきっかけ

| きっかけ | どこで分かるか |
|---|---|
| 健康診断の`WARN`・`ERROR` | 毎日の`Health check`（失敗で、GitHubからメール）。新規登録の急増・運営者の追加・運営設定の変更・運営の対処の急増・大量の削除・「RLSを回避できない」など（[運用手順](運用手順.md) 6.1） |
| 公開範囲の確認の失敗 | `Health check`の公開範囲（実際のAPI）の失敗 |
| 知らないログインの通知 | GitHub・Google・Supabase・Cloudflare・OpenAI・Resendからのメール |
| 請求・利用量の急増 | OpenAI・Resend・Supabaseの使用量 |
| GitHubの警告 | Secret scanning（鍵を書いた）・Dependabot（脆弱な部品） |
| 利用者・第三者からの連絡 | アプリ・メールでの問い合わせ |

## 2. 初動（まず30分）

1. **記録を始める**：時刻・何を見たか・何をしたかを、メモする（あとで、報告・調査に使う）。**証拠を消さない**。Supabaseのログ（Logs）は、保存期間が短い（無料プランは短い。**要確認**）ので、疑わしい部分は、**すぐ、画面を保存する**。
2. **封じ込める**（疑いの内容に合わせて、必要なものだけ。迷ったら止める）：

| 疑い | 止め方 |
|---|---|
| ボットの大量の登録・荒らし | **新規登録を止める**：運営設定 `new_signup_halted = true`（運営の設定API。[API契約](API契約.md) 7節）。緊急なら、Supabaseの Authentication の設定で、新規登録を止める。既存の利用者のログインと閲覧は、止まらない |
| 運営のアカウントが乗っ取られた | **運営者から外す**：SQL Editorで、`delete from public.admin_users where user_id = '<そのID>';`。**そのアカウントのパスワードを再設定**し、全端末からログアウトさせる（Authentication > Users）。運営の対処の記録（`moderation_actions`）で、何をされたか確認する |
| 鍵・トークンの漏れ | [運用手順](運用手順.md) 2節の表のとおり、**失効して、作り直す**。優先：Supabaseのアクセストークン・DBのパスワード → OpenAI・Resend・FCMの鍵 → 内部ジョブの秘密（`setup_internal_jobs(…, true)`）。Supabaseの secret／service_role キーは、ダッシュボードの API Keys で、新しいものを作り、古いものを無効にする（画面の名前・手順は、変わることがある。**要確認**） |
| 利用者のアカウントの乗っ取り | 該当の利用者を、利用停止（運営の対処 `suspend`）にし、パスワードの再設定を案内する |
| 大量の削除・書き換え | 運営設定を確認（`app_settings_history`）。**復旧が必要なら、[運用手順](運用手順.md) 5節（復元）**。復元では、削除の台帳で、削除済みのデータの再公開を防ぐ |
| データベースが、外から読めてしまう | `check-exposure.sh`・`check-authenticated.mjs`で、何が読めるかを確認し、原因の設定・権限を、すぐ直す。**直るまで、必要なら、プロジェクトを一時停止する**（Supabaseのダッシュボード） |

**連絡は、事実が分かってから**：利用者への告知は、「何が分かっていて、何が分かっていないか」を、分けて書く。分からないことを、推測で、断定しない。

## 3. 調べる

| 調べること | 見る場所 |
|---|---|
| いつから・何が・どこから | Supabaseの Logs（Auth・API・Postgres）。運営の記録（`moderation_actions`・`app_settings_history`） |
| GitHubの不審な操作 | リポジトリ・組織の Settings > Audit log／Security log。Actionsの実行履歴 |
| Cloudflare（ドメイン・DNS）の変更 | Cloudflareの Audit Logs。**DNSが書き換えられていないか**（メールの送信元・案内ページ） |
| メールの不審な送信 | Resendのログ（誰に・いつ・何通） |
| 外部APIの不審な利用 | OpenAIの Usage |
| **個人情報に届いたか** | `profiles`（ニックネーム・自己紹介・年齢帯）・`auth.users`（メールアドレス）・投稿・コメントに、どの範囲で届いたか。**届いていない根拠**（公開範囲の確認の結果・ログ）も、記録する |

## 4. 直す・確認する

1. 原因を直す（設定・権限・鍵・部品の更新）。
2. **鍵を作り直したことを、確認する**（古い鍵で、もう動かないこと。新しい鍵で、デプロイ・送信が動くこと）。
3. **公開範囲の確認を、もう一度、実行する**：`check-exposure.sh`（未ログイン）・`check-authenticated.mjs`（ログイン済み）。
4. 必要なら、バックアップから復元する（[運用手順](運用手順.md) 5節）。
5. **再発を防ぐ**：検知の項目・しきい値の追加（健康診断）、手順書の更新、テストの追加。

## 5. 報告・通知（法律。**要確認・専門家に相談**）

詳しい調査（出典つき）は、[法的対応](法的対応.md)の3節。ここは、事故のときに見る要約。**公式（個人情報保護委員会）のページを読んで確かめた内容**。法的な助言ではない。

**まず、報告の対象か判断する**（どれか1つに当たれば、報告の義務）

| 類型 | 条件 |
|---|---|
| **要配慮個人情報**の漏えい等 | **人数の条件はない**（1人でも）。**このアプリの投稿・自己紹介には、病気・心の不調など、要配慮個人情報が、書き込まれている可能性がある** |
| 財産的被害のおそれ | 不正利用で、財産的被害が生じるおそれ |
| 不正の目的のおそれ | 不正アクセスなど（盗難などの第三者も含む） |
| 本人の数が多い | **1,000人を超える** |

**期限**（**発覚した日から**。迷ったら、暦日で、短く数える）

- **速報：3〜5日以内が目安**（まず、分かる範囲で、速やかに）。
- **確報：30日以内**。不正の目的のおそれがある場合は、**60日以内**。
- 報告先：個人情報保護委員会の**報告フォーム**。ランサムウェアなどのサイバー攻撃の事案は、**共通様式（Excel）をメールで提出する**方法もある（宛先・件名は、公式ページで確認）。

**本人への通知**：報告の対象になる事態を**知ったとき**に、本人へ通知する義務。通知が困難なときは、**代替措置**（例：事案の公表）でよい。内容・方法・期限の目安は、**ガイドライン（通則編3-5-4）で確認する**。令和8年の改正で、「本人の権利利益の保護に欠けるおそれが少ない場合」は、通知の義務が緩和される見込み（最新の条文で確認）。

このアプリ向けの、段取り（案）：

1. **発覚した時刻を、記録する**（期限は、ここから数える）。
2. 要配慮個人情報・1,000人超・不正の目的・財産的被害のどれに当たるかを、**早めに判断する**。**迷ったら、報告する側に倒す**（速報は、分かる範囲でよい）。
3. 影響を受けた利用者への通知（アプリ内・メール。**メールは、Resendの送信元から**）。ニックネームやメールを、通知の文面に入れない。
4. 必要なら、App Store・Google Play、使っている外部サービス（Supabaseなど）のサポートへ連絡。
5. **専門家（弁護士）に、早めに相談する**。

**リリース前に決めること（未決定）**：①誰が判断・連絡するか（運営が1人なので、不在のときの代わり） ②連絡先（問い合わせ窓口、プライバシーポリシーへの記載） ③利用者への通知の文面（雛形） ④専門家への相談先。

## 6. 事後

- 起きたこと・原因・対応・再発防止を、短くまとめて、このリポジトリのIssueに残す（個人情報・鍵は、書かない）。
- 手順書（この文書・[運用手順](運用手順.md)）と、検知（健康診断）を、更新する。
