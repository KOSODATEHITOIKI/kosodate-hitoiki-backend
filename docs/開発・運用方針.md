# 開発・運用方針

更新日：2026-09-30。ドキュメントCIを導入。Supabaseのローカル開発環境を構築（Issue #8）。dev/prod環境分離とデプロイワークフローを追加（Issue #30）。本番運用手順（バックアップ・監視）は未構築。

## 1. ブランチ

**決定済み（2026-09-29）**：フロントエンドの[環境とブランチ運用ガイド](https://github.com/nakayu206/kosodate-hitoiki/blob/main/docs/環境とブランチ運用.md)に合わせ、バックエンドもdevelopを使う。作業ブランチはdevelopから作成し、変更時は必ずPRを作成する。通常の変更をmain・developへ直接コミット・pushしない。

| ブランチ | 役割 |
|---|---|
| main | リリース済みの状態 |
| develop | 開発内容の統合先 |
| feature/*・fix/* | developから分岐し、develop宛てにPR |
| hotfix/* | mainから分岐し、修正をmain・developへ反映 |

参照ガイドはPRに最低1名の承認を要求している。バックエンドのレビュー担当・ブランチ保護設定は未定。空リポジトリの初期化のみ、内容を含まない初期コミットをブランチの共通起点にする。

## Issue・PRの運用

作業をIssueで管理し、PR本文の関連Issue欄で紐づける。今回の整備は[Issue #1](https://github.com/nakayu206/kosodate-hitoiki-backend/issues/1)。PR作成後、レビューを経てマージする。

Issueテンプレート（Bug・Logic・UI）とPRテンプレートは、kosodate-hitoikiの同名ファイルをそのまま使用する。テンプレートのチェック欄は実際の確認結果だけを記入し、対象外の検証には理由を添える。

PRのbaseがdevelopの場合、Issueの自動クローズはデフォルトブランチの設定に依存する。関連付けとクローズ状態はマージ時に確認する。

## 2. ローカル開発環境（決定済み・Issue #8）

```text
docs/                  設計・運用資料
supabase/
  config.toml          ローカル設定
  seed.sql             ローカル用シードデータ（マスタ未確定のため現状は空）
  migrations/          DB・RLS・関数の変更履歴（未着手、#9・#10で追加）
  functions/           Edge Functions（未着手、#11で追加）
  tests/               DB制約・権限等の検証（未着手、#10で追加）
```

Supabase CLIはグローバルインストールに頼らず、`package.json`の`devDependencies`にバージョンを固定して`npx supabase`（または`npm run supabase:*`）で実行する。これにより新規checkoutでも`npm ci`だけで同じCLIバージョンが揃う。

### 前提

- Node.js 22以上、npm
- Docker Desktop（Supabaseのローカルスタックはコンテナで動作するため起動しておく）

### セットアップ手順

```sh
npm ci
cp .env.example .env   # 値はsupabase startの出力等で埋める。.envはコミットしない
npm run supabase:start # 初回はイメージ取得のため数分かかる
```

`supabase start`はAPI・DB・Studio・Auth・Storage等をDockerコンテナで起動し、ローカル用のURL・anon key・service_role keyを標準出力に表示する。表示された値を`.env`のSUPABASE_URL・SUPABASE_ANON_KEY・SUPABASE_SERVICE_ROLE_KEYへ転記する。マイグレーション追加後は`npm run supabase:reset`でDBを初期状態から再構築できる。

| コマンド | 内容 |
|---|---|
| `npm run supabase:start` | ローカルスタックを起動 |
| `npm run supabase:stop` | ローカルスタックを停止 |
| `npm run supabase:status` | 起動中のURL・キーを再表示 |
| `npm run supabase:reset` | マイグレーション・シードからDBを再構築 |

### 環境変数

`.env.example`に変数名と用途のみを記載する。値は各自のローカル出力・ダッシュボードから取得し、`.env`はコミットしない（ルートの`.gitignore`で除外済み）。

| 変数 | 用途 |
|---|---|
| SUPABASE_URL | ローカルスタックのAPI URL |
| SUPABASE_ANON_KEY | クライアント（Flutterアプリ）が使う公開キー |
| SUPABASE_SERVICE_ROLE_KEY | サーバー処理専用の特権キー。アプリへ配布しない |
| OPENAI_API_KEY | 送信前チェック（Moderation API）用 |

### 開発・本番の環境分離

**決定済み（2026-09-30・Issue #30）**：テスト環境と本番を分けるため、Supabaseプロジェクトを開発用（dev）と本番用（prod）の2つ用意する。リリース時のDBはprodを使う。ローカル開発はDocker上のSupabase CLIスタックのみを使い、dev・prodのどちらにも直接接続しない。

| 環境 | Supabase | 反映契機 | 用途 |
|---|---|---|---|
| local | Docker（`supabase start`） | 手動 | 開発・pgTAPテスト |
| dev | 開発用プロジェクト | `develop`へのマージで自動 | Flutter結合・動作確認 |
| prod | 本番用プロジェクト | `main`へのマージ後、承認して反映 | リリース版 |

**設計案（実装済み、運用しながら見直す）**：デプロイはGitHub Actionsの[deploy-dev.yml](../.github/workflows/deploy-dev.yml)・[deploy-prod.yml](../.github/workflows/deploy-prod.yml)が`supabase link`→`supabase db push`でマイグレーションを反映する。デプロイ前に、同じコミットのCI（`ci.yml`）が成功するまで待ち、失敗・タイムアウト時は反映しない（テストはCI側で実行し、デプロイ側では再実行しない）。dev・prodのワークフローは、それぞれ`develop`・`main`以外のrefでは動かない（Environmentのデプロイ元ブランチ制限と二重にしている）。

接続情報はGitHub Environmentごとに分けて登録する（リポジトリ・`.env`には書かない）。

| 種別 | 名前 | development | production |
|---|---|---|---|
| Secret | SUPABASE_ACCESS_TOKEN | dev用 | prod用 |
| Secret | SUPABASE_DB_PASSWORD | devプロジェクトのDBパスワード | prodのDBパスワード |
| Variable | SUPABASE_PROJECT_REF | devのproject ref | prodのproject ref |

`production`はRequired reviewersで承認者を必須とし、デプロイ元ブランチを`main`のみに制限する。`development`もデプロイ元ブランチを`develop`のみに制限する。

#### 初期設定の状況（2026-09-30）

- dev・prodのSupabaseプロジェクト作成、Environments・Secrets・Variablesの登録、`production`の承認者とブランチ制限：完了。
- Supabaseプロジェクトの作成時設定：「新しいテーブルを自動的に公開する」はオフ、「自動RLS」はオン。オフのため、テーブル・関数の権限はマイグレーションで明示する（ローカルも`auto_expose_new_tables = false`）。
- `develop`・`main`のブランチ保護でCI（`Docs and config`・`Database (migrations and RLS)`）を必須にする設定：完了（2026-09-30）。force pushと削除は禁止。PRの承認必須（Required reviewers）は、レビュー担当が未定のため未設定。CI失敗のコミットはデプロイ側でも止まる。dev環境へのマイグレーション適用（#10の10本）はdeploy-devで成功を確認済み。
- Flutterアプリは、開発ビルドにdevのURL・anon key、リリースビルドにprodのURL・anon keyを設定する（フロント側で対応）。service_role keyはアプリに配布しない。

**未対応**：Edge Functionsのデプロイ（#11で追加時にワークフローへ組み込む。関数用のシークレットも環境ごとに分ける）、prod反映前のバックアップ取得（#21）、Authのリダイレクト先・メール設定などdashboard側設定の環境差分管理。

無料枠の現行条件（プロジェクト数・一時停止条件等）は変わりうるため、プロジェクト作成前に公式情報を確認する。

## 3. 変更・検証の方針案

DB変更はマイグレーションとして残し、既に適用した変更を直接書き換えず、新しい変更で追従する。空のDBからの構築と、既存データがある状態からの更新を確認する。

実装時には次の振る舞いを重点的に検証する。**Issue #10でRLS・トリガーとして実装し、pgTAPテスト（`supabase/tests/`）で検証済み**の項目には✅を付けた。

- ✅ 未ログインでコメント本文・プロフィール本文・共感件数を取得できない（`rls_test.sql`）。
- ✅ 他人のprofiles行を直接参照できない（`rls_test.sql`）。編集はEdge Functions経由に限定（#12で実装）。
- 受付終了・ブロック・利用停止時に、APIを直接呼んでも制限が働く（`is_restricted()`関数は実装済み。実際のEdge Function側の確認は#11〜#13で実装）。
- ✅ 返信の階層（1段階のみ）、親コメントの投稿一致、ニックネーム・通報の重複制約を守る（`schema_test.sql`・`business_rules_test.sql`）。
- ✅ 通報3人到達での自動一時非表示、再表示後の再集計なしを確認（`business_rules_test.sql`）。同時リクエストでの競合はDB制約（部分unique index）に委ねる。
- 送信前チェックを迂回できず、編集時にもチェックする（Edge Functions側の実装は#11〜#13）。
- 投稿削除・退会・途中失敗からの再実行が保持要件と整合する（削除カスケード・保持期間はスキーマに反映済み、退会フロー自体は#20で実装）。
- 管理操作に運営者権限と二段階認証を要求する（`is_admin()`によるRLS制御は実装済み。二段階認証必須化はEdge Function側で#11以降に実装）。

### 現在のCI

GitHub Actionsの`CI`で、develop・main宛てPRと両ブランチへのpushを検証する。3つのチェックが並行実行される。

#### Docs and config

- markdownlint-cli2でMarkdownの見出し・リスト等を検証する。日本語の長文・表に合わせ、行長と表の列幅の制約は無効化する。
- 共通のIssue・PRテンプレートは原本を維持するためMarkdown lintから除外する。
- Prettierでworkflow YAMLとルートのJSONの構文・整形を確認する。GitHub Actions固有の意味検証やリンク切れ検証は含まない。
- 読み取り権限のみで実行し、Supabaseの秘密情報やデプロイ権限は使わない。

#### Database (migrations and RLS)（Issue #10で追加）

- `supabase start`でローカルスタックを起動し、`supabase/migrations/`を空DBへ適用する。
- `supabase test db`でpgTAP（`supabase/tests/`）を実行し、テーブル・制約の存在、RLSの権限境界、トリガーによる業務ルールを検証する。
- `npm run test:functions-integration`（`supabase/tests/functions/run.sh`）で、Edge Functionsの配線をローカルのAuth・DB・Storageへ実際に接続して検証する（送信前チェックの外部APIだけフェイク）。
- `npm run test:concurrency`（`supabase/tests/concurrency/run.sh`）で、2本のpsqlを並行させる競合テストを実行する。同時通報での3人到達、ニックネームの旧名予約と同時登録、同名の同時新規登録を検証する（pgTAPは1セッションのため別スクリプトにしている）。
- ローカルDockerスタックのみで完結し、外部の秘密情報・本番接続情報は使わない。

#### Functions (types and tests)（Issue #11で追加）

- Denoをnpmのdevディペンデンシー（`deno`、バージョン固定）として使い、`supabase/functions/`を検証する。このジョブだけ、Denoの実行ファイル取得のため`npm ci`を`--ignore-scripts`なしで実行する。
- `npm run functions:check`：`deno fmt --check`・`deno lint`・`deno check`（型検査）。
- `npm run functions:test`：`deno test --frozen`。判定ロジック（個人情報・禁止語・閾値）、外部API障害、本文・APIキーをログや例外へ漏らさないこと、チェックした本文と保存本文の一致を検証する。外部APIはモックで、実際のOpenAI APIは呼ばない。
- 実際のModeration APIに評価例を通す`npm run functions:eval`はCIでは実行しない（`OPENAI_API_KEY`と課金が必要なため）。

ローカルでもNode.js 22とDockerで同じ検証を実行できる。

```sh
npm ci --ignore-scripts
npm run check
npm run supabase:start
npx supabase test db
npm run supabase:stop
```

依存関係はpackage-lock.jsonに固定する。リンク先と内容の整合はレビューで確認する。Edge Functionsの検証は、実装を追加するPR（#11以降）でCIに組み込む。

ブランチ保護による必須チェックの設定は別途必要。CIの追加だけでは、失敗時のマージを強制的に禁止する設定にはならない。

## 4. 秘密情報・ログの方針案

APIキー、特権キー、認証用秘密情報をGitへ保存しない。設定例には変数名と用途だけを記載する。投稿本文や認証情報をエラーログへ無条件に出力しない。特権を使う処理は呼び出し元の本人確認・権限確認を明示する。

## 5. バックアップと復旧

**決定済み**：無料プランでの開始にあたり、自前の定期バックアップを必須とし、暗号化して非公開で保管する。削除済みデータも一定期間でバックアップから消えるようにする。

未決定：取得頻度、保持期間、保管先、対象データ、暗号鍵の管理、復旧目標、失敗の通知先。

**設計案**：バックアップが取得できたことに加え、隔離した環境で復元できることを確認する。退会・削除済みデータが復元によって再公開されない手順を定義する。DB以外の認証設定・秘密情報など、別途復旧が必要なものを洗い出す。

料金・無料枠・一時停止条件は変わりうるため、環境構築時に公式情報を確認する。本資料は現行料金や利用可能機能を保証するものではない。
