# 認証設定

更新日：2026-09-30。Issue #12。メール・Google・Appleログインの担当境界、外部設定の手順、検証手順、残作業を記録する。**決定済み**：ログイン方法はメールアドレス・Google・Appleの3つ（Notion決定ログ 2026-09-28）。**設計案**：以下の担当分けと手順は実装時の案であり、外部サービスの画面・条件は変わりうるため、設定時に公式情報を確認する。

## 1. 担当境界

| 領域 | 担当 | 内容 |
|---|---|---|
| 認証そのもの（メール・パスワード、Google、Apple、トークンの発行・更新） | **Supabase Auth**（バックエンドの設定） | プロバイダの有効化、クライアントID・シークレットの登録、リダイレクトURLの許可 |
| ログイン画面・OSのサインインUI・トークンの保持 | **Flutter（フロントエンド）** | `supabase_flutter`でのサインイン、Google／Appleのネイティブサインイン、ログイン状態の保持（Notion決定：期限なしで保持） |
| プロフィールの作成・更新・画像・ニックネーム変更、利用規約同意の記録 | **Edge Functions**（本リポジトリ、`profile-*`） | 認証済みの`user_id`を必ずサーバー側で確認して処理する。クライアントからの`user_id`の自己申告は使わない |
| 外部サービス側の設定（Google Cloud・Apple Developer・メール送信元） | **管理者（手作業）** | 下記の手順 |

認証情報（パスワード・トークン・プロバイダのシークレット）はリポジトリに含めず、Supabaseのダッシュボードまたはシークレットストアでのみ管理する。`public_profiles`・APIレスポンスには、メールアドレスなどの認証情報を含めない。

## 2. 新規登録の流れ

1. Flutterが Supabase Auth でアカウントを作る（メール／Google／Apple）。この時点では`auth.users`だけで、プロフィールはない。
2. Flutterが利用規約への同意とニックネーム等を入力させ、`POST /functions/v1/profile-create`を呼ぶ。
3. Edge Functionがニックネーム・自己紹介を送信前チェックにかけ、`create_profile`（1トランザクション）でプロフィール・利用規約同意・通知設定を作る。
4. 途中で失敗した場合は全体が取り消され、中途半端な登録は残らない。応答が届かず再送した場合、同じ内容なら重複せず成功を返す（`200`）。別のニックネームで再登録しようとすると`409 CONFLICT`。
5. プロフィールが未作成の利用者は、投稿・コメント等の書き込みを行えない（#13以降でEdge Function側が確認する）。

## 3. 外部設定の手順と残作業（管理者・dev／prodそれぞれ）

| 項目 | 手順の概要 | 状態 |
|---|---|---|
| メール認証 | Supabaseダッシュボード Authentication > Providers > Email を有効化し、「Confirm email」（メール確認を必須）を確認する。無料枠の送信制限に注意 | dev：**有効（メール確認は必須）**を、APIの設定（`mailer_autoconfirm: false`）で確認済み（2026-10-21）。prod：未実施 |
| メールのテンプレート（日本語） | 下の「メールのテンプレートを入れる手順」。登録の確認・パスワードの再設定・メールアドレス変更・パスワード変更の通知。**自分用のSMTPを設定しないと、ダッシュボードでは編集できない** | ローカル：**実施済み・動作確認済み**（4種類とも日本語で届く）。dev・prod：**未実施。SMTPの決定待ち**（devで、編集画面に「Set up custom SMTP to edit templates」と出て編集できないことを確認した・2026-10-21） |
| メール送信（SMTP） | 本番のメール送信サービス。Supabase標準の送信は、回数の制限が小さく、日本語化もできない。**本番では必須**（リリース前に決める）。無料枠のあるサービスの多くは、自分のドメインの設定が必要で、費用や手間がかかる場合がある | **未決定** |
| 確認後の戻り先（Site URL） | メールのリンクを押したあとに開くページ。静的ページ（「メールの確認が済みました。アプリに戻って、ログインしてください」）を、GitHub Pagesで公開した（`KOSODATEHITOIKI/kosodate-hitoiki-site`、URL：`https://kosodatehitoiki.github.io/kosodate-hitoiki-site/`）。Supabaseの Authentication > URL Configuration > Site URL に設定する | dev：**設定済み（管理者の報告・2026-10-21）。実際の登録で、リンクのあとにページが出るかは未確認**。prod：未実施（リリース時に同じURLを設定する） |
| Google | Google CloudでOAuthクライアント（Web・iOS・Android）を作成し、クライアントIDとシークレットをSupabaseのGoogleプロバイダへ登録。承認済みのリダイレクトURIにSupabaseのコールバックURLを追加 | **未実施** |
| Apple | Apple DeveloperでServices ID・Sign in with Appleのキーを作成し、Supabaseの Apple プロバイダへ登録。iOSアプリではネイティブサインインを使う（Apple Developer Programへの加入が必要） | **未実施** |
| リダイレクトURL | Authentication > URL Configuration に、アプリのディープリンク（Flutter側で決定）を許可リストとして登録。dev用・prod用で分ける | **未実施**（URLはフロントと調整） |
| 環境の分離 | dev・prodのSupabaseプロジェクトそれぞれに、別のクライアントID・シークレットを登録する | 未実施 |

`supabase/config.toml`の`[auth]`はローカル開発用で、リモートのdev・prodには反映されない（リモートはダッシュボードで管理）。ローカルではメール認証のみ動作し、Google・Appleは無効のまま。

### メールのテンプレートを入れる手順（管理者の手作業・dev／prodそれぞれ）

**前提：先に、自分用のSMTP（Authentication > Emails > SMTP Settings）を設定する。** 標準のメール送信のままだと、ダッシュボードの編集画面に「Set up custom SMTP to edit templates」と出て、件名・本文を編集できない（英語の標準テンプレートに固定される）。SMTPは未決定なので、**メールの日本語化は、SMTPを決めてから行う**。

テンプレートの正本は`supabase/templates/*.html`と、`supabase/config.toml`の件名（`[auth.email.template.*]`）。SMTPを設定したあと、ダッシュボードには、同じ内容を貼る。

| ダッシュボードの項目（Authentication > Emails > Templates） | 件名 | 本文（貼るファイル） |
|---|---|---|
| Confirm sign up | 【ひと息】メールアドレスの確認 | `supabase/templates/confirmation.html` |
| Reset password | 【ひと息】パスワードの再設定 | `supabase/templates/recovery.html` |
| Change email address | 【ひと息】メールアドレス変更の確認 | `supabase/templates/email_change.html` |
| （Notifications）Password changed | 【ひと息】パスワードを変更しました | `supabase/templates/password_changed_notification.html` |

- 本文のファイルの中身を、そのまま「Message body」に貼る（変数`{{ .ConfirmationURL }}`などは、そのまま）。「Source」表示（HTML）で貼ること。
- 差出人名・送信元は、SMTPの設定で決まる（SMTPは未決定）。Supabase標準のメール送信は、回数の制限が小さく、日本語化もできないため、本番前にSMTPを決める。
- 件名・本文を変えたら、`supabase/templates/`と`config.toml`を先に直し、ダッシュボードへ貼り直す（正本とずれさせない）。
- 文面には、**未決定の値（再設定リンクの有効時間、再送間隔）を書いていない**。決まってから足す。
- **パスワード再設定は、アプリのディープリンクが決まるまで、最後まで完了できない**（リンクの先でアプリを開いて新しいパスワードを入れる必要があるため）。メールの文面だけ先に用意してある。

## 4. 検証手順

### 自動（CI）

`npm run test:functions-integration`が、ローカルのAuth・DB・Storageに実際に接続して、登録→再送→ニックネーム変更（初回可・30日制限）→更新→画像アップロード・差し替え・削除→直接書き込みの拒否を確認する。送信前チェックの外部API（OpenAI）だけはフェイク。

### 手動（外部設定のあと、dev環境で）

1. メール：登録すると確認メールが届く（**日本語になるのは、SMTPを設定してから**。それまでは英語の標準）。リンクを押すと**戻り先のページ**（「メールの確認が済みました。アプリに戻って、ログインしてください」）が開き、アプリでログインできる。
2. Google：アプリからGoogleでサインインし、`auth.users`にユーザーが作られる。
3. Apple：iPhone実機でAppleでサインインし、`auth.users`にユーザーが作られる。
4. いずれも、サインイン後に`profile-create`を呼び、`profiles`・`terms_acceptances`・`notification_settings`が1件ずつできる。
5. 同じ操作を再送しても重複しない。別のユーザーで同じニックネームを登録すると`409`になる。
6. 画像をアップロードし、`public_profiles.avatar_path`から公開URLで表示できる。

## 5. 未決定

- **確認後の戻り先ページ**：置き場所は**GitHub Pages（組織`KOSODATEHITOIKI`の`kosodate-hitoiki-site`）に決定**（2026-10-21）。本番のSite URLにも、同じページを使うか（文面が共通でよいか）は、リリース前に確認する。
- **戻り先を、アプリのディープリンクへ変える**：Googleログイン・パスワード再設定にも同じ設定が必要。形式はフロントと決めてから、Supabaseの「Redirect URLs」に登録する。

- **パスワード条件・メール確認の要否**：Notionの決定ログでは未決定。現在のローカル設定（最小6文字、確認メールなし）は初期値で、確定値ではない。
- **利用規約の本文・版の付け方**：`terms_version`は運営が付ける文字列。規約本文と法務確認は別工程（[未決事項](未決事項.md)）。規約改定時の再同意フローは未設計。
- **対象利用者の範囲**（養育者の範囲・年齢制限）：未決定。登録時の確認方法に影響する。
- **アカウント連携**（同じメールでGoogle・Appleを使った場合の統合）：未検討。`enable_manual_linking`は無効のまま。
- **新規登録の停止（#18、実装済み）**：Authの`before_user_created`フック（`public.hook_before_user_created`）が、停止中はメール・Google・Appleのどの経路でもアカウントの作成を拒否する。ローカルは`config.toml`で有効化済み（実際のメール登録で、停止中に拒否・再開後に成功を確認）。**クラウド（dev・prod）は、Supabaseダッシュボードの Authentication > Auth Hooks で「Before User Created」を「Postgres function」として`public.hook_before_user_created`に設定する必要がある（手作業。未設定でも、`profile-create`が新しいプロフィールを拒否する第二の防御は効く）**。Google・Appleの実機での停止の確認は、#12の外部設定が済んでから行う。
