# AWS移行設計案

更新日：2026-10-20

> **状態：保留（2026-10-20、利用者の決定）**。本番はSupabaseのまま運用する。AWSの最小構成は月 約$85（約1.3万円、目安）で、Supabase Pro（月 約$25）より高く、予算と両立しないため。AWSは、バックアップの保管先（S3）だけに使う。この文書は、将来移行するときの設計として残す。段階1・2の検証（Supabaseなしで全マイグレーションと権限が通ること）は、CIで保っている。

バックエンドをSupabaseからAWSへ移す設計。移行の方針・範囲・方式の6点は**決定済み**。構成の細部・手順・見積もりは**設計案**で、段階ごとに確定する。

**決定済み（2026-10-20、利用者）**：

- 移行する方針と範囲：バックエンド全体（Supabase→AWS）。目的は「いまの市場の標準がAWSであるため」。
- 方式は、推奨案をすべて採用する（下の6点）。
  1. REST API：PostgRESTをFargateで動かす（フロントとRLSの設計を保つ）。
  2. ログイン：Cognito。
  3. IaC：AWS CDK（TypeScript）。
  4. AWSアカウント：devとprodを別アカウントにする。
  5. 時期：**移行を終えてからリリースする**（Supabaseではリリースしない）。
  6. 日本語検索：pg_bigm（再測定する）。
- 要調査として残る：運営の二段階認証済み（`aal2`相当）をCognitoで再現できるか（段階0で調査）。

**設計案**：以下の構成・手順・見積もりは、実現方法の提案（方式の6点は決定済み。細部は段階ごとに確定する）。

## 1. 先に押さえる前提

- **リリース前の今が、最も安く移せる時期**。既存の利用者のデータ移行も、アプリの強制更新も要らない。リリース後に移すと、これらが必要になる。
- 移行で最も危ないのは、**これまでの安全対策（deny-by-default、RLS、二段階認証、権限テスト）が、移行の途中で崩れること**。移行中は、公開範囲と権限の検証を、各段階で必ずやり直す。
- 運営の負担が増える。パッチ適用、鍵の管理、監視、バックアップを、Supabaseに任せられなくなる（[運用セキュリティ](#7-運用セキュリティリリース前の必須確認)）。

## 2. 方針：SQLと権限の設計を捨てずに、土台だけ入れ替える

今のバックエンドの価値の大部分は、**SQLのマイグレーション、RLS、権限テスト（pgTAP）、Edge Functionsの業務ロジック**にある。これらはSupabase固有ではなく、PostgreSQLと標準のWeb APIで書いてある。そこで、**捨てずに残し、土台（ログイン、API、保存先、実行環境）だけをAWSに入れ替える**。

| 役割 | 今（Supabase） | AWS（設計案） | 備考 |
|---|---|---|---|
| データベース | Postgres 17 | RDS for PostgreSQL 17（プライベートサブネット、公開しない）。規模が増えたらAurora | マイグレーションとRLSは、そのまま使う |
| ログイン | Supabase Auth | Amazon Cognito（メール、Google、Apple、TOTP） | 下の「互換層」で、`auth.users`・`auth.uid()` を保つ |
| REST API（読み取り、RLS） | PostgREST | **PostgRESTをそのまま、ECS Fargateで動かす** | フロントのREST呼び出しとRLSを保てる。JWTはCognitoのJWKSで検証 |
| サーバー処理（投稿、退会、通報など） | Edge Functions（Deno） | Lambda（Denoのコンテナイメージ＋Lambda Web Adapter）。API GatewayまたはALB経由 | 業務ロジックは変えず、接続部分（wiring）だけ入れ替える |
| 画像の保存 | Storage | S3（非公開）＋CloudFront（公開）。アップロードはLambda経由 | 公開は画像のURLだけ。一覧は不可 |
| 定期実行 | pg_cron | pg_cron（RDSで利用可）＋EventBridge | DB内の処理はpg_cronのまま。外部を呼ぶものはEventBridge |
| 日本語検索 | PGroonga | **pg_bigm**（RDSで利用可）に変更。要再測定 | PGroongaはRDSの対応が確認できない。方式が変わるので、[検索方式の実測](検索方式の実測.md)をやり直す |
| 秘密情報 | Supabase/GitHubのシークレット | Secrets Manager。GitHub ActionsからはOIDC（長期の鍵を持たない） | キーをチャットやリポジトリに置かない方針は同じ |
| バックアップ | 自前（pg_dump→R2案） | RDSの自動バックアップ（35日まで）＋自前のpg_dumpをS3（Object Lock）へ | 保持30日。復元で削除済みが戻らない仕組み（台帳）は、そのまま使える |
| プッシュ配信 | FCM | FCM（変更なし） | |
| 送信前チェック | OpenAI Moderation | OpenAI Moderation（変更なし） | |

### 互換層（Supabase固有の部分を、小さな層で代替する）

マイグレーションがSupabaseの機能に依存している箇所は少なく、次の層で吸収する。

- `auth.users(id uuid)`：Cognitoの利用者IDと対応する最小のテーブル。登録の確認後のトリガー（Cognitoのpost-confirmation）で作る。外部キーは今のまま使える。
- `auth.uid()`・`auth.role()`・`auth.jwt()`：PostgRESTが設定する `request.jwt.claims` を読む関数。RLSとビューは今のまま動く。
- ロール `anon`・`authenticated`・`service_role`：PostgRESTが切り替える。権限（grant）は今のまま。
- `auth.sessions`：退会の本人確認が使うセッションの作成時刻。Cognitoのトークンの `auth_time` で代替し、`session_started_at` を差し替える。
- Cognito側で付けるクレーム：`role`（pre-token-generation）。運営者の二段階認証済みを示す印（`aal2` 相当）は、Cognitoが認証にMFAを使ったかを示す情報から作る。**これが実現できるかは要調査**（できないと、運営の二段階認証の仕組みを設計し直す）。

## 3. 段階的な進め方

各段階の終わりに、**公開範囲と権限の検証（pgTAP、実機のAPI呼び出し）を通す**ことを完了条件にする。

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 0 | 決定事項の確定、AWSアカウントの構成、IaCの雛形 | [未決事項](未決事項.md)の項目が決まり、devの環境が作れる |
| 1 | 互換層を作り、**Supabaseなしの素のPostgres 17**で、全マイグレーションとpgTAPを通す | pgTAP全件成功（これがSupabaseから離れられることの証明。ローカルで先にできる） |
| 2 | RDSを作り、PostgRESTをFargateで動かし、Cognito（JWKS）でJWT検証。匿名・本人・運営者の権限を実機で検証 | 権限テストと、実機の公開範囲の検証が全件成功 |
| 3 | Edge FunctionsをLambdaへ（接続部分の差し替え）。結合テストを通す | 結合テスト全件成功 |
| 4 | 画像をS3とCloudFrontへ。メタデータ除去、削除待ち、退会時の削除 | 画像まわりの結合テスト成功 |
| 5 | 日本語検索をpg_bigmへ。再測定 | 検索方式の実測で、PGroongaと同等以上の精度・速度 |
| 6 | 運用：バックアップ、監視、WAF、秘密情報、GuardDuty、CloudTrail | 復元の自動検証、リリース前チェックリスト完了 |
| 7 | Flutterアプリの切り替え（ログインはCognito、REST先とFunctionsの宛先を変更） | 受け入れ確認（#22） |
| 8 | prodの作成と、リリース | 手順を確認したリリース工程 |

**段階1は、AWSを触らずにできる**。Supabaseから離れられる見込みの有無を、最小の費用で確かめられる。

**段階1の状況（2026-10-20）**：完了。`infra/portable/run.sh` が、素のPostgres 17（pgTAPとpg_cronを加えたもの）に、互換層（`infra/portable/compat.sql`）と全マイグレーションを適用し、**pgTAP全件（15ファイル・475件）を通す**。CI（`Portable Postgres (no Supabase)`）で保つ。Supabase側のテストも変わらず通る。マイグレーション側の変更は2か所だけで、Supabase上の動作は変えていない：①Storageのバケット作成は、storageスキーマがあるときだけ、②PGroongaの拡張・索引は使える環境だけで作り、無い環境では索引なしの代替の検索にする（段階5でpg_bigmに置き換える）。

**段階2の状況（2026-10-20）**：ローカルで検証済み（`infra/portable/rest.sh`）。PostgREST（Supabaseと同じ16.3）を素のPostgres 17の上で動かし、**実際のHTTPのAPI**に、本物のJWTの形式のトークンで問い合わせて、未ログイン・本人・他人・運営者（`aal1`と`aal2`）・不正なトークンで、見える範囲が想定どおりであることを確かめた（34項目）。CI（`Portable Postgres (no Supabase)`）で保つ。確認した主な点：

- 未ログインは、公開マスタと公開ビューだけ。機密テーブル・投稿者IDの列・書き込み用の関数は拒否される。
- 本人は自分の通知・プロフィール本文だけ。他人の分は見えず、既読にもできない。宛先は書き換えられない。
- 投稿・プロフィールの**直接の書き込みはできない**（サーバー処理の鍵だけ）。
- 運営の画面（通報の一覧・運営設定）は、`aal2`のときだけ見える。
- 別の鍵で署名したトークン、署名なし（`alg:none`）、署名を改ざんしたトークン、署名が不正な`service_role`の主張、`role=postgres`の主張は、いずれも特権を得られない。
- 期限切れのトークンは拒否される。PostgRESTは、時計のずれに備えた**ごく短い猶予（数十秒）**を持つ（2分以上前に切れたものは拒否される）。

**残る点（段階2のAWS側）**：JWTの検証を、テスト用の共有鍵からCognitoのJWKSに替える。Cognitoのトークンに`role`と`aal`の印を付ける（pre-token-generation）。これは、AWSに環境を作る段階で確認する。

## 4. 見積もり（目安）

厳密な見積もりではない。実際の費用はAWSの料金計算ツールで確認する。

- 作業量：段階1〜6で数週間規模。フロントの切り替え（段階7）は、別リポジトリの作業。
- 月額費用（目安、東京リージョン、小規模）：RDS（小さいインスタンス）、Fargate（PostgREST）、ロードバランサー、NATゲートウェイまたはVPCエンドポイント、CloudFront、S3、Secrets Manager、監視。**Supabase Proより高くなる**ことが多い。固定費の中心は、ロードバランサー、NAT、RDS。

## 5. リスク

| リスク | 対策 |
|---|---|
| 運営者の二段階認証済み（`aal2`）をCognitoで再現できない | 段階0で調査。できなければ、運営向けAPIだけ別の認証方式（例：運営用のユーザープール＋MFA必須）にする |
| pg_bigmの検索精度・速度が足りない | 段階5で再測定。足りなければOpenSearch等を検討（費用と運用が増える） |
| 移行中に権限が崩れる | 各段階で権限テスト・実機検証。`api_privileges_test` と同等の検証を、PostgREST越しにも行う |
| IaCの設定ミスで公開（S3、RDS、セキュリティグループ） | 非公開を既定にし、AWS Config・Access Analyzerで検知。RDSは公開しない |
| 運用の人手が足りない | マネージドサービスを優先。監視・アラートを最初から入れる |

## 6. 決めたこと（2026-10-20）と、残る調査

| 項目 | 決定 | 退けた案 |
|---|---|---|
| REST API | PostgRESTをFargateで動かす | すべてLambdaで作り直す（作業が大きく、安全対策の検証をやり直す） |
| ログイン | Cognito | ほかのIdP |
| IaC | AWS CDK（TypeScript） | Terraform |
| AWSアカウント | devとprodを別アカウント | 単一アカウント |
| 時期 | 移行を終えてからリリース | Supabaseでリリースして後から移す（データ移行とアプリ更新が必要になる） |
| 日本語検索 | pg_bigm（再測定する） | OpenSearch（費用と運用が増える） |

**進め方（2026-10-20）**：段階2〜5は、まずローカルで作って検証する（費用なし）。AWSに実際の環境を作るのは、利用者の合図のあと。予算（月200円）との両立は未解決（[未決事項](未決事項.md)）。

**要調査**：運営の二段階認証済み（`aal2`相当）をCognitoで再現できるか。段階0で調べ、できなければ運営向けの認証方式を設計し直す。

## 7. 運用セキュリティ（リリース前の必須確認）

コードの検証だけでは、実際の漏洩リスクは評価できない。次を、リリース前の必須確認とする（[開発・運用方針](開発・運用方針.md)、[運用手順](運用手順.md)）。

1. AWS・GitHub・運営アカウントの**MFAと権限**（rootは使わない、IAM Identity Center、最小権限）。
2. 本番のDB・S3・APIの**公開範囲を、実際のAPIで検証**する（dev・prodの差分に注意）。
3. 特権キー・シークレットの保管場所、使用者、失効（ローテーション）の手順。
4. 削除ジョブ（画像の削除待ち、保持期限、台帳）の定期実行と、失敗の監視。
5. 外部API（OpenAI、FCM）に送るデータと、保持条件の確認。
6. 依存ライブラリ・ランタイムの更新方針（脆弱性の悪用までが速い）。
