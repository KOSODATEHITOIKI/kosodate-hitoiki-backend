# 送信前チェック評価

更新日：2026-09-30。Issue #11。送信前チェック（[バックエンド設計](バックエンド設計.md)4節）の判定方式・閾値の初期案と、日本語の評価例、その判定結果を記録する。**方式と閾値は設計案であり、公開前に実例で調整する**（調整前の値を確定事項として扱わない）。

## 1. 決定済みの前提と設計案

| 区分 | 内容 |
|---|---|
| 決定済み | 対象は投稿・コメント・返信・ニックネーム・自己紹介（新規・編集とも）。禁止語リストとOpenAI Moderation APIで開始。外部API障害時は保存をブロックして再試行を促す。危害のほのめかしは止めず、本人にだけ相談先を案内する。イニシャル・公人・作品名は機械的に禁止しない |
| 承認済みの方針（2026-09-30） | 正規表現による電話番号・住所らしき文字列の検出＋禁止語＋Moderation APIの組み合わせ。閾値は公開前に実例で調整。誤判定の異議申立ては通報経路を流用 |
| 設計案 | 下記の判定フロー、`reject`と`confirm`の2段階、閾値の初期値 |

## 2. 判定フロー（設計案）

実装は`supabase/functions/_shared/moderation/`。各Edge Functionは`moderateAndSave()`だけを経由して保存する。

1. **ローカル判定**（外部APIを呼ばない）：禁止語または個人情報らしき文字列（電話番号・メールアドレス・郵便番号・住所）があれば`reject`。個人情報らしき文字列を外部サービスへ送らないためでもある。
2. **Moderation API**（`omni-moderation-latest`）：カテゴリ別スコアを閾値と比べる。
   - 攻撃・差別・脅迫が明確（`reject`閾値以上）：`reject`（HTTP 422 `MODERATION_REJECTED`）
   - 境界域（`confirm`閾値以上）：`confirm`（HTTP 409 `MODERATION_CONFIRM_REQUIRED`）。`confirmed: true`を付けた再送は許可する。`reject`は確認しても覆らない
   - 自分・子どもへの危害のほのめかし（`self-harm`系・`violence`）：投稿は止めず、書き込んだ本人にだけ`support_notice`で相談先を案内する
3. **API障害**（キー未設定・通信断・タイムアウト・非2xx・想定外の応答。**判定に使うカテゴリが欠けた・0〜1の数でない応答も、想定外として扱う**。空のスコアを「問題なし」と判定して、不適切な内容を保存しないため。画像は、`sexual/minors`だけ、なくてもよい〔あれば検証〕。テキスト専用のカテゴリで、画像の応答に含まれない可能性があるため）：保存せずHTTP 503 `MODERATION_UNAVAILABLE`。例外・ログに本文・APIキー・応答本文を含めない。

チェックした本文と保存本文の一致：`moderateAndSave()`は入力を複製・凍結したうえで判定し、保存関数へ**同じ凍結済みの値**だけを渡す。チェック後に本文を書き換えたり、クライアントが申告した結果を使ったりする経路を作らない。書き込みはService Role（Edge Functions）に限り、クライアントの直接書き込みはRLSで拒否済み（[スキーマ定義](スキーマ定義.md)10節）。

### 閾値（`policy.ts`、評価例38件の実測にもとづく初期値）

| 区分 | カテゴリ | スコア | 実測にもとづく変更 |
|---|---|---|---|
| reject | harassment | 0.85 | 変更なし（下記の限界を参照） |
| reject | harassment/threatening | **0.4** | 0.5から変更。放火の脅迫が0.46で通過していた |
| reject | hate/threatening | 0.5 | 変更なし（実測の例なし） |
| reject | hate | **0.5** | 0.7から変更。差別表現が0.57で確認止まりだった |
| confirm | harassment | 0.5 | 変更なし |
| confirm | hate | 0.4 | 変更なし |
| 相談先案内 | self-harm | **0.10** | 0.4から変更。「死ねなくてつらい」が0.16で案内が出なかった |
| 相談先案内 | self-harm/intent | **0.08** | 0.3から変更。「子どもといなくなりたい」が0.10で案内が出なかった |
| 相談先案内 | self-harm/instructions | 0.3 | 変更なし |
| 相談先案内 | violence | 0.6 | 変更なし |

案内は、出しすぎても害が小さい（書いた本人にだけ表示する、支える方向の案内）ため、**漏れを減らす側に寄せている**。一方、止める閾値（reject）は、愚痴を止めないことを優先して慎重に動かす。

ローカルの補助：APIが検知しない表現（子どもへの加害の不安など）のため、`support_phrases.ts`の表現リストでも案内を出す。他者への直接の死の願望（「消えてしまえ」「いなくなれ」「くたばれ」）は、既存の「消えろ」と同様に禁止語（`banned_words.ts`）で止める。自分への「消えてしまいたい」「いなくなりたい」は止めない。

### 実測の結果（2026-10-15、`omni-moderation-latest`、38件）

実際のAPIに評価例を通した結果を、閾値を調整する前の判定と、調整後の判定で示す。判定に使うスコアは、`measured_scores_test.ts`に記録し、閾値を変えても愚痴を止めないことを回帰テストで確認している（外部APIを呼ばない）。

| 区分 | 件数 | 調整前 | 調整後 |
|---|---|---|---|
| 愚痴（g1〜g10） | 10 | すべて許可（g5「死にそう」は案内あり） | 同じ。**止めた愚痴は0件** |
| 境界（b1〜b4、m1〜m3） | 7 | b1〜b4・m1・m2は許可、m3「クソ旦那」は確認 | 同じ |
| 個人情報（p1〜p5） | 5 | すべて拒否（ローカル、APIは呼ばない） | 同じ |
| 攻撃（a1〜a8） | 8 | **a5・a7は確認止まり、a8（放火の脅迫）は通過** | すべて拒否（a5は禁止語、a7はhate閾値、a8は脅迫閾値） |
| 危害示唆（h1〜h8） | 8 | **h2・h3・h4・h5・h8で案内が出なかった** | すべて案内あり（h3・h8はAPIが検知せず、表現リスト） |

実測で分かったこと：

- **愚痴と攻撃は、harassmentのスコアだけでは区別できない**。「クソ旦那。ほんとに使えない」（愚痴）が0.81、「お前なんか消えてしまえ。ばばあ」（攻撃）が0.64。愚痴を止めないため、rejectの閾値（0.85）は下げず、攻撃のうち拒否に届かないものは、確認表示・通報・運営の確認に任せる。直接の死の願望など、はっきりした表現は禁止語で補う。
- **APIは、子どもへの加害の不安を検知しない**。「子どもに手を上げてしまいそうで怖い」は、全カテゴリが0.00〜0.02。ローカルの表現リストで補う。
- **「死にそう」のような愚痴の誇張は、自殺関連のスコアが高く出る**（g5：self-harm 0.52）。案内は出るが、止めない（意図どおり）。

**限界（重要）**：閾値は、この38件に合わせた調整であり、**少数の例への過学習の可能性がある**。実際の投稿の言い回し・長さ・分布とは異なる。公開前に、実例（運営が集めた実際の言い回し、通報された投稿）で再測定して調整する。

### アカウント画像（Issue #12）

アップロード画像は保存前にOpenAI Moderationの画像判定で確認する（`omni-moderation-latest`、画像はdata URLで送る）。確認表示は挟まず、次のいずれかが閾値以上なら保存しない。閾値は未調整の初期値（`policy.ts`の`IMAGE_REJECT_THRESHOLDS`）：sexual 0.5、sexual/minors 0.1、violence/graphic 0.6、self-harm/instructions 0.5。顔・子どもの判別は行わない。実測は未取得（APIキー未設定）。

## 4. 未検証・未決定

- **Moderation APIの日本語精度**：38件で実測した（上記）。愚痴と攻撃はharassmentのスコアで区別できず、子どもへの加害の不安は検知されない。禁止語・表現リストで補っているが、**網羅は狭い**（例：「消えろ」「消えてしまえ」は止まるが、ほかの言い回しは未確認）。実例で増やす。
- **個人情報の検出漏れ**：名前、SNSのID、LINE ID、勤務先・学校名、「〇〇小学校の3年生」のような間接的な特定は機械的に検出しない。URLも現状は対象外。追加するかは実例を見て判断する。
- **住所の検出**：都道府県名から始まる表記のみ。「世田谷区代田1-2-3」のように都道府県を省くと検出しない。
- **禁止語リスト**：運営が実例を見て追加・調整する。誰が更新し、どこで管理するか（コード内か設定テーブルか）は未決定。
- **確認表示を無視して送った場合の扱い**：`confirm`は`confirmed: true`の再送で許可し、`reject`は覆らない、という初期案を実装した。この境界は未決定事項として残す（[未決事項](未決事項.md)）。
- **相談先案内の出しすぎ**：案内は閾値を低めにしており、本人にだけ表示する。「死にそう」のような愚痴の誇張にも出る。出しすぎが負担になるかは、実際の利用で確認する（案内の文言・頻度の抑制は未決定）。
- **相談先の内容**（電話・URL・文言）：未決定。APIは`support_notice`のフラグだけを返し、文言はクライアント側で持つ想定。
- **異議申立て**：誤判定は通報経路を流用する方針だが、窓口・対応時間は未決定。
- **コスト・レート制限**：Moderation APIの利用量は投稿頻度制限（#18）と合わせて見直す。
