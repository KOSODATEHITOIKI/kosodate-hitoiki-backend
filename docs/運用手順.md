バックアップ・復旧・デプロイ・監視の手順（Issue #21）。**決定済み**＝利用者が決めた要件、**設計案**＝実現方法の提案、**未決定**＝判断が残るもの。

関連：[開発・運用方針](開発・運用方針.md)、[退会とデータの保持](退会とデータの保持.md)、[AWS移行設計案](AWS移行設計案.md)

## 1. 担当と連絡先

| 役割 | 担当 | 通知先 |
|---|---|---|
| 運用の責任者（バックアップ・監視・復旧の判断） | リポジトリの管理者（現在は1人） | GitHub Actionsの失敗メール、予算アラートのメール |

## 2. 環境と秘密情報

| 環境 | 用途 | 反映 | 秘密情報の置き場所 |
|---|---|---|---|
| local | 開発・テスト | 手動 | `.env`（本番の値は書かない） |
| dev | 結合確認 | `develop`へのマージで自動 | GitHub Environment `development` |
| prod | 本番 | `main`へのマージ＋承認 | GitHub Environment `production` |
| backup-development / backup-production | バックアップ・台帳・監視 | スケジュール | GitHub Environment `backup-*`（下記） |

秘密情報の種類・置き場所・使う人・失効の手順。**秘密情報は、チャットやリポジトリに置かない**。登録は、管理者が自分の端末から行う。

| 秘密 | 置き場所 | 使う処理 | 失効（漏れたとき） |
|---|---|---|---|
| Supabaseのアクセストークン（環境ごと） | GitHub Environment `development`/`production` の Secret | デプロイ（`supabase db push`、関数の配備） | Supabaseのダッシュボードで削除し、作り直す。期限を長めに、スコープを最小に |
| DBのパスワード（環境ごと） | 同上 | デプロイ | ダッシュボードでパスワードを再設定し、Secretを更新 |
| OpenAI APIキー | Edge Functionsのシークレット（`supabase secrets set`）、GitHubの Secret | 送信前チェック | OpenAIのダッシュボードで失効し、作り直す |
| FCMのサービスアカウントの鍵 | Edge Functionsのシークレット `FCM_SERVICE_ACCOUNT_JSON` | プッシュ配信 | Firebaseで鍵を削除し、作り直す |
| 内部ジョブの秘密 | **DBのVaultにだけ**（DBの中で作る。誰も値を見ない。`setup_internal_jobs`） | `push-dispatch`・`storage-cleanup`を呼ぶcron | `setup_internal_jobs(…, true)`で入れ替える |
| バックアップ用のDB接続文字列 `BACKUP_DATABASE_URL`（**読み取り専用ロール**） | GitHub Environment `backup-*` の Secret | バックアップ・台帳・監視 | そのロールのパスワードを再設定し、Secretを更新 |
| バックアップ暗号化の**公開鍵** `BACKUP_AGE_RECIPIENTS` | GitHub Environment の Variable（公開してよい） | バックアップの暗号化 | 鍵を追加・差し替える（古い鍵で暗号化済みのものは、古い秘密鍵が必要） |
| バックアップの**秘密鍵** | **管理者のオフライン保管（パスワード管理ツール＋紙などの別の保管場所）。GitHub・サーバーには置かない** | 復元のときだけ | 紛失すると復元できない。2か所以上に保管する |
| 保管先（S3互換。R2を例にする）のAPIトークン `R2_ACCESS_KEY_ID`／`R2_SECRET_ACCESS_KEY`（**環境ごとに別のバケット・別のトークン**） | GitHub Environment `backup-*` の Secret。トークンは、そのバケットだけの「Object 読み取りと書き込み」に絞る | バックアップ・台帳の保管、監視（最新の確認） | R2でトークンを削除し、作り直してSecretを更新 |
| 保管先の接続先 `R2_ENDPOINT_URL`、バケット名 `BACKUP_BUCKET` | GitHub Environment の Variable（秘密ではない） | 同上 | 保管先を移すときに差し替える |
| 復元用のR2トークン（**読み取り専用**） | **GitHubには置かない**。管理者のパスワード管理ツール | 復元のときだけ | R2でトークンを削除し、作り直す |

**手動判断点**：秘密情報を新しく登録・失効するのは、必ず管理者。AIエージェント（Claude Code）には、秘密の値を渡さない。

## 3. デプロイ（適用順と失敗時の復旧）

### 3.1 適用順

1. PRが`develop`へマージされると、CI（`Database`・`Docs and config`・`Functions`・`Portable Postgres`）が成功してから、`deploy-dev`が動く。
2. `deploy-dev`は、①マイグレーション（`supabase db push`）→②Edge Functionsの配備の順に反映する。**DBを先、関数を後**にする（新しい関数が古いDBで動く期間を作らないため）。
3. devで確認してから、`main`へのPRを作る。マージ後、`deploy-prod`が**承認待ち**で止まる。承認者が、対象（コミット・マイグレーションの一覧）を確認して承認する。
4. 本番反映の前に、**必ずバックアップを取る**（手動実行：Actionsの`Backup`→`production`）。

### 3.2 失敗したとき

| 状況 | 対応 |
|---|---|
| マイグレーションが途中で失敗 | `supabase db push`は、失敗した1本を戻す。原因を直した**新しいマイグレーション**を追加して再反映する。**適用済みのマイグレーションは編集しない**（他の環境と食い違う） |
| マイグレーションは通ったが、アプリが壊れた | 先に関数だけを前の版に戻す（`git revert`→`develop`/`main`）。DBは前に進めたまま、互換を保つ。戻せない変更（列の削除など）は、事前に2段階に分ける |
| データを壊した・消した | 4節のバックアップから、**隔離した環境で**復元して確認し、必要な分だけを戻す |
| 本番で緊急修正が必要 | `hotfix/xxx`を`main`から切り、`main`と`develop`の両方へ反映する |

**手動判断点**：本番への反映の承認、復元して本番へ戻す判断、利用者への告知。

## 4. バックアップ

> **保管先は未定（2026-10-21）**。AWSは使わない方針（[未決事項](未決事項.md)）。Cloudflare R2は、無料枠だけでもカードの登録が必要なため見送った。以下は、**S3互換の保管先（R2・Backblaze B2など）を使う場合の設計**。`infra/aws/`のテンプレートは使わない（AWSへ移すときのために残している）。ワークフローは`aws s3`に、接続先（`--endpoint-url`）とアクセスキーを渡して動かす（変数名は`R2_*`）。今は`BACKUP_DEV_ENABLED`／`BACKUP_PROD_ENABLED`が未設定なので、バックアップのワークフローは何も実行しない。リリース前に、4.3の初期設定を行う。

### 4.1 方式（決定済み・2026-10-20）

- 取得：**毎日1回**（日本時間 午前2時台）。GitHub Actionsの`Backup`。
- 内容：データだけ（`public`と`auth`の`users`・`identities`・`mfa_factors`）。構造は、マイグレーションで作る。
- **含めない**：Storageの画像ファイル（利用者がいつでも再アップロードできる。削除済みの画像が復元で再公開されないように）、セッション・一時トークン・監査ログ、配信キュー。**復元後は、全員が再ログインになる**。
- 保管先：**Cloudflare R2**（非公開のバケット。環境ごとに別）。**暗号化してから**置く（`age`、公開鍵で暗号化。秘密鍵は管理者のオフライン）。バケットは公開しない（`r2.dev`の公開URLとカスタムドメインを有効にしない）。バケットに**Bucket Lock**（Age、30日。30日間は削除・上書き不可）を付ける。
- **R2の鍵の限界**：R2のAPIトークンには、書き込み専用がない（「読み取りと書き込み」か「読み取り専用」）。GitHubに置くトークンは、そのバケットだけの「読み取りと書き込み」にする。**トークンが漏れても、①中身は`age`で暗号化済みで読めない、②Bucket Lockの間は削除・上書きできない**ので、バックアップは守られる。ロックの期間を過ぎた古いものと、新しい名前での追加は、漏れた場合に許してしまう（そのときはトークンを失効する）。
- 保持：**30日**（決定済み）。R2のオブジェクトのライフサイクル（削除）で、**31日**で自動削除する（ロックの30日が切れてから消す）。
- 取得に使う接続は、**読み取り専用のロール**（書き込みできない）。
- 検証：**取得のたびに**、使い捨てのデータベースへ復元し、主要テーブルの件数がダンプの前後の範囲に収まることを確かめる。失敗したらバックアップを保管せず、ジョブを失敗にする。
- 台帳：削除の台帳（IDと時刻だけ）を、**1時間ごと**に別に書き出す（`Ledger export`）。

### 4.2 失敗の検知

1. ジョブの失敗 → GitHubからメール（リポジトリの管理者）。
2. 毎日の`Health check`が、最新のバックアップが36時間以内、台帳が3時間以内であることを確認する（止まっていたら失敗）。
3. **定期実行そのものが止まる**場合（スケジュールは、リポジトリに60日動きがないと無効になる）に備え、成功のたびに外部の見張り（healthchecks.ioなど）へ通知し、通知が途絶えたらメールが来るようにする（**任意・手作業**）。

### 4.3 初期設定（管理者の手作業）

1. **暗号化の鍵を作る**（自分のPCで）。`age-keygen -o backup-key.txt`。表示される`age1...`が公開鍵。`backup-key.txt`（秘密鍵）は、**パスワード管理ツールと別の場所の2か所に保管**し、PCに残さない。**秘密鍵の中身をチャットに貼らない。**
2. **R2に保管先を作る**（環境ごとに1回。Cloudflareのアカウントは二段階認証を有効にしておく）。
   - バケットを作る（例：`kosodate-backup-dev`／`kosodate-backup-prod`）。**公開設定（r2.dev、カスタムドメイン）は有効にしない。**
   - バケットの設定で、**Bucket Lock**（Age、30日）と**ライフサイクル**（31日で削除）を追加する。
   - **APIトークンを作る**（R2 → Manage API tokens）：権限は「Object 読み取りと書き込み」、対象は**そのバケットだけ**。表示される`Access Key ID`と`Secret Access Key`は、**一度しか表示されない。チャットに貼らず**、手順4でGitHubへ直接入れる。
   - 復元用に、**別の「Object 読み取り専用」トークン**を作り、パスワード管理ツールにだけ保管する（GitHubには置かない）。
   - 接続先は、`https://<アカウントID>.r2.cloudflarestorage.com`（R2の画面の「S3 API」に表示される）。
3. **読み取り専用のDBロールを作る**（SupabaseのSQL Editorで、環境ごと）。

   ```sql
   create role backup_reader login password '<強いパスワード>';
   grant pg_read_all_data to backup_reader;
   alter role backup_reader set default_transaction_read_only = on;
   ```

   接続文字列は、Supabaseの「Session pooler」（IPv4）で、ユーザー名を`backup_reader.<project-ref>`にする。**パスワードをチャットに貼らない。**
4. **GitHubに登録する**（管理者の端末で`gh`を使うか、画面で）。
   - Environment `backup-development`/`backup-production`を作る（prodは承認者を設定）。
   - Environment の Secret：`BACKUP_DATABASE_URL`、`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`、（任意）`HEALTHCHECK_PING_URL`。
   - Environment の Variables：`R2_ENDPOINT_URL`、`BACKUP_BUCKET`、`BACKUP_AGE_RECIPIENTS`（公開鍵）、`SUPABASE_URL`、`SUPABASE_ANON_KEY`（公開キー）。
   - リポジトリの Variables：`BACKUP_DEV_ENABLED`／`BACKUP_PROD_ENABLED` を`true`にした環境だけ動く。
5. **手動で1回実行**して、成功を確認する（Actions→`Backup`→Run workflow）。

**注意**：スケジュール実行と手動実行は、デフォルトブランチ（`main`）にあるワークフローでしか動かない。初回リリースまでは`main`にないため、**devに対してだけ**、バックアップ関連のファイル（`scripts/ops/`、ワークフロー、マイグレーション）を`develop`に取り込んだときにも自動で実行する（`push`トリガー。本番には実行しない）。これでリリース前に、devで動作を確認できる。

## 5. 復元（隔離した環境で）

**本番のデータを上書きする前に、必ず隔離した環境で復元して確認する。**

1. **新しいSupabaseプロジェクト**（または使い捨てのローカル）を用意し、`main`のマイグレーションを適用する（`supabase db push`／`supabase start`）。
2. R2から（復元用の読み取り専用トークンで）、対象のバックアップ（`backups/<環境>/日付/backup-*.tar.age`）と、**取得後の台帳**（`ledger/<環境>/…`の、バックアップより新しいものすべて）をダウンロードする。
3. 秘密鍵で復号する：`age -d -i backup-key.txt backup-….tar.age | tar -xf -`。`dump.pgdump`と`manifest.json`が出る。
4. 復元する：`DST_DB_CONTAINER=… bash scripts/ops/restore.sh dump.pgdump ledger.json`（台帳を複数ある場合は、`jq -s 'add'`などで1つに結合）。**台帳を渡さないと、取得後に削除したデータが復活する。**
5. 確認する：主要な件数、ログイン（再ログインが必要）、公開範囲（`check-exposure.sh`）。
6. 問題がなければ、本番への戻し方を判断する（プロジェクトごと切り替える／必要な行だけ戻す）。**手動判断点。**

**削除済みデータの再公開を防ぐ仕組み**：削除（投稿・コメント・退会）は、DBが台帳に自動で記録する（35日保持）。復元のあとに台帳を取り込み、`replay_deletion_ledger()`で再び削除する。**残るリスク**：台帳の書き出しは1時間ごと。書き出しの間（最大1時間）の削除は、DBごと失った場合に戻る可能性がある。検証は`scripts/ops/verify-local.sh`（バックアップ→削除→復元で復活→台帳で再削除）。

画像ファイルはバックアップに含めないため、画像が復元で再公開されることはない（プロフィールの`avatar_path`が指す画像が無い場合は、利用者が再アップロードする）。

## 6. 監視

### 6.1 毎日の健康診断（`Health check`、失敗でメール）

| 項目 | しきい値 | 見る理由 |
|---|---|---|
| DBの容量 | 400MB（無料枠500MBの80%） | 無料枠で止まる前に気づく |
| 登録者数 | 40,000（月間アクティブ5万の80%の目安） | 無料枠・料金の変化 |
| 未対応の通報 | 3日を超えたら | 運営の対応の遅れ |
| 削除に5回以上失敗した画像 | 1件でも | 公開されたまま残る恐れ（至急） |
| 1日以上削除されていない画像 | 1件でも | 削除ジョブの停止 |
| プッシュ配信の失敗（24時間） | 20件 | FCMの設定・障害 |
| 溜まったプッシュ | 1時間以上 | 配信ジョブの停止 |
| 定期実行（pg_cron）の失敗（48時間） | 1件でも | まとめ通知・期限切れの削除の停止 |
| バックアップの鮮度 | 36時間 | バックアップの停止 |
| 台帳の書き出しの鮮度 | 3時間 | 台帳の停止 |
| 公開範囲（実際のAPI） | 想定外が1つでも | 設定ミスによる意図しない公開 |

### 6.3 ログと個人情報

- Edge Functionsのログには、本文・メール・ニックネーム・端末トークン・APIキー・DBのエラー本文を**出さない**（エラー名だけ）。実装とテストで保っている。
- Supabase・GitHub Actionsのログは、提供元の保持期間に従う。ワークフローは、秘密を`echo`しない。接続文字列はSecretとして自動でマスクされる。
- 暗号化前のバックアップは、ジョブの中で使い捨ての領域にだけ置き、暗号化後すぐに削除する。

## 8. 内部ジョブの定期実行（プッシュ配信・画像の削除待ち）

### 8.1 仕組み（決定済み・2026-10-20）

Supabaseの機能だけで完結する。新しい外部サービスと費用はない。

- DBの中の**pg_cron**が、**pg_net**（DBからHTTPを呼ぶ拡張）で、Edge Functionsを呼ぶ（`public.invoke_internal_job`）。
  - `push-dispatch`（プッシュ配信）：**1分ごと**。
  - `storage-cleanup`（画像の削除待ちの処理。失敗した画像の再試行）：**10分ごと**。
- 呼び出しの秘密は、**DBの中で作り、Supabase Vault（暗号化された保管庫）にだけ置く**。**誰も値を見ない**。リポジトリ・GitHub・Edge Functionsのシークレットには置かない（2か所に置くと、貼り付けのずれで食い違い、動かなくなる。実際にdevで起きた）。
- 2つの関数は、受け取った秘密（`x-job-secret`ヘッダー）が正しいかを、**DBに問い合わせて**確かめる（`job_secret_valid`。service_roleだけが呼べる）。**秘密がない・違う・未登録のときは404**を返し、存在を明かさない。ゲートウェイのJWT検証は`config.toml`で外している（cronにはJWTがないため）。
- 呼べるのは、許可した2つの名前だけ（任意のURLは呼べない）。`invoke_internal_job`・`setup_internal_jobs`は、DBの管理者（postgres）だけが実行できる。
- 秘密か接続先が未登録の環境では、何も呼ばずに終わる（登録するまで、ジョブは動かない）。

### 8.2 初期設定（管理者。環境ごとに1回：dev・prodで別の秘密になる）

SupabaseのSQL Editorで、**次の1行**を実行するだけ。コピー・貼り付け・PowerShellは要らない。`<ref>`は、そのプロジェクトのref（devは`djbizophhqtlqmlabhdo`）に置き換える。

```sql
select public.setup_internal_jobs('https://<ref>.supabase.co');
```

`秘密を新しく作りました。接続先：https://<ref>.supabase.co` と返れば成功（秘密の値は返らない）。すでに設定済みなら、`秘密はすでにあります（変更しません）`と返り、秘密は変わらない。

**動作を確認する**（SQL Editor）：

```sql
select public.invoke_internal_job('storage-cleanup');
-- 10秒ほど待ってから
select id, status_code, left(content::text, 80) as content from net._http_response order by id desc limit 3;
```

`status_code`が`200`なら成功。`push-dispatch`は、FCMが未設定の間は`503`（`プッシュ配信の設定がありません`）が正常で、秘密の照合が通った証拠。`404`は、秘密が未登録（上の1行を実行していない）、またはEdge Functionsが古い版（配備を確認する）。理由は、Supabaseの Edge Functions > 各関数 > Logs の`job-secret rejected: …`で調べる（秘密の値は出ない。受け取った文字数だけが出る）。

**公開範囲を確かめる**：`check-exposure.sh`が、`push-dispatch`・`storage-cleanup`を秘密なしで呼んで404になることを確認する。

### 8.3 秘密の入れ替え（漏れたとき・定期的に）

```sql
select public.setup_internal_jobs('https://<ref>.supabase.co', true);
```

秘密が新しくなり、古い秘密は直ちに無効になる。cronは次の実行から新しい秘密を使うので、他に作業はない（Edge Functionsの更新も不要）。

### 8.4 失敗の検知

- 毎日の`Health check`が、削除に5回以上失敗した画像・1日以上削除されていない画像・1時間以上溜まったプッシュを検知する（ジョブが止まっていることに気づく）。
- 実行の履歴：`select * from cron.job_run_details order by start_time desc limit 10;`（cronの実行）、`net._http_response`（Edge Functionsの応答）。
