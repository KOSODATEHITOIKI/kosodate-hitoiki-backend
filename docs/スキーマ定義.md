# スキーマ定義

更新日：2026-09-30（Issue #12：アカウント画像・利用規約同意・ニックネームのロックを追加）。Issue #9として[データ設計案](データ設計案.md)・[バックエンド設計](バックエンド設計.md)・[未決事項](未決事項.md)の決定済み要件を具体化した、テーブル定義の一次資料。**本書のテーブル名・カラム名・型は実装時の名称とする**（データ設計案は経緯と論点の記録として残す）。マイグレーションSQL・RLS・DBテストはIssue #10で`supabase/migrations/`・`supabase/tests/`として実装済み。

型はPostgreSQL（Supabase）を前提とする。すべてのテーブルは`created_at timestamptz not null default now()`を持つ（記載省略）。主キーは特記なき限り`id uuid primary key default gen_random_uuid()`。

## 2. プロフィール・ニックネーム

### profiles

| カラム | 型 | 制約・備考 |
|---|---|---|
| id | uuid | PK、`references auth.users(id) on delete cascade` |
| nickname | text | 表示用。2〜12文字（絵文字等は1文字として数える。文字数チェックはEdge Function側でNFKC正規化＋グラフェムクラスタ単位に行い、DBは`char_length(nickname) between 1 and 24`程度の緩い上限のみ持つ） |
| normalized_nickname | text | 一意判定用。NFKC正規化＋大文字小文字統一＋前後空白除去した値。`unique`制約 |
| icon_key | text | 用意されたイラストから選択（マスタは[未決事項](未決事項.md)参照。初期版確定までは自由入力のkeyとして保持）。`avatar_path`とは排他 |
| avatar_path | text | 利用者がアップロードした画像のStorageパス（`avatars`バケット内、`<user_id>/<ファイル名>`）。`icon_key`とは排他（`check (icon_key is null or avatar_path is null)`）。書き込みはEdge Functionsのみ |
| bio | text | 任意、100文字まで |
| child_age_range | text | 任意。選択肢は未決定のためテキストで保持し、確定後にenum化を検討 |
| updated_at | timestamptz | 編集のたびに更新 |

**決定済み**：本名・住所・電話番号・子どもの名前は収集しない。プロフィール本文（bio・child_age_range）は本人と運営者のみが参照でき（2026-09-30決定・初期版）、nicknameとicon_keyのみ`public_profiles`ビューで投稿上に公開表示する（[バックエンド設計](バックエンド設計.md)2節）。他のログイン済み利用者への本文公開は、プロフィール閲覧画面が必要になった時点で判断する（[未決事項](未決事項.md)）。

**決定済み（2026-09-30・Issue #12）**：アカウント画像は「用意したイラストを選ぶ」か「自分の画像をアップロードする」のどちらか一方を選べる。アップロードは、形式JPEG・PNG・WebP、サーバー受付は2MBまで（アプリ側で512px四方に縮小）、投稿上でニックネームと一緒に公開、アップロード時にOpenAI Moderationの画像判定で確認し不適切ならブロック（API障害時は保存しない）、クライアントからStorageへ直接アップロードせずEdge Functionが確認後に保存する。画像を変更したときは旧画像を削除し、退会時も削除する。顔写真・子どもの写真を避ける注意書きをアプリで表示する（文言は案）。

**設計案**：`normalized_nickname`はDBトリガー（`before insert or update`）で`nickname`から自動生成し、アプリ側の計算とズレないようにする。正規化アルゴリズム（NFKC適用範囲、絵文字の扱い）はEdge Function・トリガーの実装時に確定する。

### terms_acceptances

| カラム | 型 | 制約・備考 |
|---|---|---|
| user_id | uuid | `references auth.users(id) on delete cascade` |
| terms_version | text | 同意した利用規約の版（運営が付ける文字列、1〜40文字） |
| accepted_at | timestamptz | 同意日時 |

複合PK`(user_id, terms_version)`。**設計案**：登録時と規約改定時にEdge Functionsが記録する。本人は自分の分だけ参照でき、クライアントからの直接書き込みは不可。規約本文・版の付け方・法務確認は未決定（[未決事項](未決事項.md)）。

### nickname_reservations

| カラム | 型 | 制約・備考 |
|---|---|---|
| normalized_nickname | text | PK |
| reserved_until | timestamptz | 変更・退会から30日後 |
| previous_owner_id | uuid | 元の利用者。退会時はauth.usersの削除後も残すため`on delete set null`は使わず、退会処理内でこの値を保持したままauth.usersのみ削除する運用とする |
| reason | text | `changed`（ニックネーム変更）／`withdrawn`（退会） |

**決定済み**：予約期間中は他者が同じ`normalized_nickname`を使用できないが、`previous_owner_id`本人は再利用できる（[未決事項](未決事項.md)反映済み）。

**決定済み（2026-09-30・Issue #12）**：ニックネームの変更・登録は、新旧の正規化名を名前単位のアドバイザリロックで直列化する（`profiles_before_write()`）。旧名を手放すトランザクションと、その名前を登録するトランザクションが同時に走っても、後者が予約を見逃さない。同じ名前の同時新規登録は一意制約で1人だけ成功する。検証は`supabase/tests/concurrency/run.sh`（CIで実行）。

**設計案**：ニックネーム変更・登録時は`profiles`の一意制約チェックに加えて、`nickname_reservations`に他者予約が有効（`reserved_until > now()`）でないかを確認する。本人が同じ名前へ「変更」した場合は新規予約を作らない。

## 3. 投稿・コメント・話題

### topics

| カラム | 型 | 制約・備考 |
|---|---|---|
| id | smallint | PK |
| label | text | 運営が用意する話題名 |
| sort_order | smallint | 表示順 |
| is_active | boolean | 選択肢からの除外に使う（削除せず非表示） |

初期の選択肢は未決定（[未決事項](未決事項.md)「マスタ選択肢の初期版」）。確定後に`supabase/seed.sql`へ反映する。

### posts

| カラム | 型 | 制約・備考 |
|---|---|---|
| id | uuid | PK |
| author_id | uuid | `references auth.users(id)` |
| post_type | text | `check (post_type in ('guchi','soudan','kotsu'))`（ぐち／相談／コツ・体験談） |
| topic_id | smallint | `references topics(id)`、null可（任意で1つ） |
| body | text | 1,000文字まで。`check (char_length(body) between 1 and 1000)` |
| reaction_mode | text | `check (reaction_mode in ('quiet_support','want_comments'))`。初期値`quiet_support`（ただ聞いてほしい） |
| comment_acceptance | text | `check (comment_acceptance in ('open','closed'))`。`reaction_mode='want_comments'`のときのみ意味を持つ |
| edited_at | timestamptz | 本文が実際に変わったときだけ設定する「編集済み」の判定用（updated_atは反応モード変更でも変わるため使わない） |
| hidden_at | timestamptz | 通報による自動一時非表示。nullなら非表示でない |
| updated_at | timestamptz | 編集のたびに更新 |

**決定済み**：投稿種類・話題は決定済み（[バックエンド設計](バックエンド設計.md)3節）。`reaction_mode`は相互に変更可能、`comment_acceptance`は`want_comments`のときのみ`open`⇄`closed`を切り替える。投稿削除時は`comments`・`reactions`・`saved_posts`の関連行を`on delete cascade`で削除する。

**設計案**：`hidden_at`が設定された投稿は一般利用者・未ログイン利用者からのSELECTを公開ビュー・RLSで除外する。運営者は`hidden_at`の有無に関わらず参照できる。

### comments

| カラム | 型 | 制約・備考 |
|---|---|---|
| id | uuid | PK |
| post_id | uuid | `references posts(id) on delete cascade` |
| author_id | uuid | `references auth.users(id)` |
| parent_comment_id | uuid | `references comments(id) on delete cascade`、null可 |
| body | text | 500文字まで。削除済みの場合はnull |
| edited_at | timestamptz | 本文が実際に変わったときだけ設定する「編集済み」の判定用 |
| deleted_at | timestamptz | 本人削除時に設定。null以外なら「削除済み」として表示しbodyを返さない |
| hidden_at | timestamptz | 通報による自動一時非表示、または親投稿の一時非表示に連動 |
| updated_at | timestamptz | 編集のたびに更新（「編集済み」表示の判定に使用） |

**決定済み**：返信は1段階のみ（[バックエンド設計](バックエンド設計.md)3節）。表示順は`created_at asc`、返信は対象コメントの下に表示する。親コメント削除時は本文を「削除済み」として扱い、返信は残す。削除済み・一時非表示のコメントは公開コメント件数に含めない。

**設計案**：`parent_comment_id`が指すコメントの`post_id`が自分自身の`post_id`と一致すること、および指すコメント自身の`parent_comment_id`がnull（＝返信への返信を禁止）であることを、`before insert`トリガーで検証する（Postgresの標準FK制約だけでは表現できないため）。コメント削除は物理削除ではなく`deleted_at`を設定するソフト削除とし、`body`をnullへ更新する（削除時点の本文を保持しない）。

### reactions

| カラム | 型 | 制約・備考 |
|---|---|---|
| post_id | uuid | `references posts(id) on delete cascade` |
| user_id | uuid | `references auth.users(id)` |
| reaction_type_id | smallint | `references reaction_types(id)` |
| updated_at | timestamptz | 変更のたびに更新 |

主キーは`(post_id, user_id)`の複合PK。

**決定済み**：共感ボタンと定型文は1つのリアクションに統一済み（[バックエンド設計](バックエンド設計.md)2節）。ログイン必須、1投稿1人1つで変更・取消可能、コメント受付終了後も利用可能。件数は投稿者のみ閲覧可。

**設計案**：登録は`insert ... on conflict (post_id, user_id) do update set reaction_type_id = excluded.reaction_type_id, updated_at = now()`で変更を一操作にする。取消は行の削除。

### saved_posts

| user_id | uuid | `references auth.users(id)` |
| post_id | uuid | `references posts(id) on delete cascade` |

### hidden_items

| カラム | 型 | 制約・備考 |
|---|---|---|
| user_id | uuid | `references auth.users(id)` |
| target_type | text | `check (target_type in ('post','comment'))` |
| target_id | uuid | 対象のid（`posts`または`comments`への論理参照。型ごとにFKを分けるのが難しいためアプリ層で整合性を保証する） |

複合PK`(user_id, target_type, target_id)`。**本人だけに**非表示にする機能で、運営の一時非表示（`hidden_at`）とは独立に扱う。

### blocks

| カラム | 型 | 制約・備考 |
|---|---|---|
| blocker_id | uuid | `references auth.users(id)` |
| blocked_id | uuid | `references auth.users(id)`、`check (blocker_id <> blocked_id)` |

複合PK`(blocker_id, blocked_id)`。**決定済み**：ブロックすると相手の投稿・コメント・返信が自分に表示されず、相手は自分の投稿・コメントへコメント・返信・共感できない。相手には通知しない。

## 6. 通報・運営操作・利用制限

### reports

| カラム | 型 | 制約・備考 |
|---|---|---|
| id | uuid | PK |
| reporter_id | uuid | `references auth.users(id)` |
| target_type | text | `check (target_type in ('post','comment'))` |
| target_id | uuid | 論理参照（削除後も記録を残すため物理FKを張らない） |
| reason | text | 通報理由（6種、Notion決定ログ参照） |
| detail | text | 補足、任意 |
| resolved_at | timestamptz | 運営が再表示・削除等で対処した日時。nullは未対応 |
| resolved_by | uuid | 対処した運営者 |

**決定済み**：同一通報者・同一対象の通報は1件に集約する。運営が対処（`resolved_at`設定）した後は、その通報群を「3人到達」の自動非表示判定に再カウントしない。

**設計案**：一意制約は`unique (reporter_id, target_type, target_id) where resolved_at is null`という部分unique indexにする。これにより、対処済みの通報が残っていても、対処後に同じ通報者が新たに通報し直せる（過去の対処済み行とは別の未対応行として扱う）。自動一時非表示は「`target_type`・`target_id`が一致し`resolved_at is null`である行」を`reporter_id`でdistinctカウントし、3人に達したら対象の`hidden_at`を設定するトリガー／DB関数で行う。運営が再表示するときは、対象の`resolved_at is null`な通報をまとめて`resolved_at = now()`に更新する。

### moderation_actions

| カラム | 型 | 制約・備考 |
|---|---|---|
| id | uuid | PK |
| admin_id | uuid | `references auth.users(id)` |
| target_type | text | `check (target_type in ('post','comment'))` |
| target_id | uuid | 論理参照 |
| action | text | `check (action in ('unhide','delete','warn','suspend'))` |
| target_owner_id | uuid | 挿入時点の投稿者・コメント投稿者。`delete`で対象が消えた後も本人への理由通知を参照できるよう保持する |
| reason | text | 本人へ通知する理由 |

運営者の全操作を記録する。書き込みはEdge Functions（service_role）経由のみ、参照範囲は[権限表](権限表.md)で定義する。

### account_restrictions

| カラム | 型 | 制約・備考 |
|---|---|---|
| id | uuid | PK |
| user_id | uuid | `references auth.users(id)` |
| stage | smallint | 1=7日間、2=30日間、3=無期限。次の`stage`は当該利用者の過去件数から決定する |
| starts_at | timestamptz | 開始日時 |
| ends_at | timestamptz | 終了予定。`stage=3`（無期限）はnull |
| reason | text | 対処理由 |
| created_by | uuid | 運営者 |
| lifted_at | timestamptz | 異議申立て等による早期解除。運用は未決定（[未決事項](未決事項.md)） |

**決定済み**：利用停止は段階的（初回7日→再発30日→再発以降は無期限）。停止中は新規投稿・コメント・共感・通報を禁止し、既存の投稿・コメントは公開を維持する。

**設計案**：現在有効な制限は`ends_at is null or ends_at > now()`かつ`lifted_at is null`で判定する。新規制限作成時は`select count(*) from account_restrictions where user_id = :id`で次の`stage`を決める（`lifted_at`済みも含めるか、悪質性評価の一部とするかは運用ルールとして別途定める）。

## 8. 運営設定

### admin_users

| カラム | 型 | 制約・備考 |
|---|---|---|
| user_id | uuid | PK、`references auth.users(id)` |

運営者アカウントを表す（Issue #10で実装）。`is_admin()`関数（`security definer`）がこのテーブルを参照し、RLSポリシーから運営者判定に使う。書き込みはEdge Functions経由のみ。

### app_settings

| カラム | 型 | 制約・備考 |
|---|---|---|
| key | text | PK。現在のキーは`new_user_limit`・`new_signup_halted`（下記） |
| value | jsonb | 設定値 |
| updated_by | uuid | 運営者 |
| updated_at | timestamptz | |

**決定済み**：登録直後のレート制限・新規登録停止は固定値でなく本テーブルで運営がトグル・変更できるようにする（[バックエンド設計](バックエンド設計.md)7節）。

| key | value | 初期値（**暫定**。運営が変更できる） |
|---|---|---|
| `new_user_limit` | `{ "enabled", "window_hours", "max_posts", "max_comments" }` | 有効、登録後24時間、投稿1件、コメント3件 |
| `new_signup_halted` | true／false | false（停止していない） |

- 変更は`set_app_setting`（service_role専用のDB関数）だけ。運営者の登録を確認し、値の形・範囲（`window_hours`は1〜720、件数は0〜1000）を検証し、**未知のキーは作らせない**。直接の書き込みポリシーはない。
- 変更のたびに`app_settings_history`へ（キー・前の値・新しい値・変更した運営者・日時）を残す。参照は運営者（二段階認証済み）だけ。
- `write_events`（user_id・kind・created_at）：登録直後の制限の回数に使う、投稿・コメントの作成の記録。**投稿・コメントを削除しても回数は戻らない**よう、別に持つ。service_role専用（ポリシーなし）。30日を過ぎたものは次回の作成時に削除する。
- 回数は、利用者ごとのadvisory lockで直列化する。同時の作成でも上限を超えない（`supabase/tests/concurrency/run.sh`）。運営者は対象外。窓は`profiles.created_at`から測る。
- 新規登録の停止は二重に効く：Authの`before_user_created`フック（`public.hook_before_user_created`。メール・Google・Appleのどの経路でも、アカウントの作成そのものを拒否）と、`create_profile`（停止中は新しいプロフィールを作らない。作成済みの再送は成功を返す）。

## 9. 未確定のまま残す設計判断

- `child_age_range`・`icon_key`・`muted_words`件数上限：マスタ選択肢が未決定のため型を仮置きしている。確定後にenum化・CHECK制約を追加する（[未決事項](未決事項.md)）。
- ニックネーム正規化の具体アルゴリズム：NFKC正規化を軸に置くが、絵文字・結合文字の扱いは実装時に確定する。
- `account_restrictions`の異議申立て・早期解除の運用フロー：`lifted_at`カラムは用意するが、承認プロセスは未決定。
- 通報理由の具体的な6種の値：Notion決定ログの記述を採用予定だが、本書では`reason`をtextとして仮置きしている。実装時にCHECK制約またはマスタテーブル化を検討する。

## 10. Issue #10で確定したRLS方針（実装済み）

マイグレーション実装時に以下の方針を確定した（設計段階では未確定だった点）。

- **送信前チェック対象のテーブル（`profiles`のnickname/bio、`posts`、`comments`）には、認証済み利用者向けのINSERT/UPDATE/DELETE RLSポリシーを一切設けない。** 書き込みはすべてEdge Functions（`service_role`、RLSをバイパスする）経由に限定し、クライアントからのPostgREST直接書き込みで送信前チェックを迂回できないようにする（[バックエンド設計](バックエンド設計.md)4節の要件を、RLS設計として具体化したもの）。同様に`reports`・`moderation_actions`・`account_restrictions`・`nickname_reservations`・`app_settings`も直接書き込みポリシーを設けない。
- 一方、自由記述を伴わない単純な関係のトグル（`reactions`・`saved_posts`・`hidden_items`・`blocks`・`muted_topics`・`muted_words`・`notification_settings`・`push_devices`）は、本人限定のRLSポリシーで直接操作を許可する。
- 共感件数（投稿者のみ閲覧可）は`reactions`テーブルへの直接SELECTでは実現できない（他者の行が見えてしまうため）ため、`get_post_reaction_count()`という`security definer`関数を介して提供する。同様に公開コメント件数は`post_comment_count()`関数で提供し、未ログイン利用者にコメント本文へのアクセス経路を与えずに件数だけを返す。
- プロフィールの公開列（nickname・icon_key・avatar_path）は、`profiles`本体のRLS（本人・運営者限定）とは別に、`security_invoker`を付けない`public_profiles`ビュー（オーナー権限で実行）で公開する。PostgreSQL 15以降の`security_invoker = true`はRLSに阻まれて0件になるため、この用途には使わない。

### 11. API権限の締め直し（2026-10-13・deny-by-default）

**決定済み**：APIの公開設定ミスによる情報漏洩は許容しない。`anon`・`authenticated`の権限は、移行`20260930120000_lockdown_api_privileges.sql`でいったん全て外し、必要なものだけを明示して付ける。

- 未ログインは、公開マスタ（`topics`・`reaction_types`）、公開ビュー（`public_posts`・`public_profiles`）、`posts`の公開列（`author_id`を除く）、公開コメント件数の関数だけ。`posts`テーブルから`author_id`（利用者ID）は取れない。
- `TRUNCATE`・`TRIGGER`・`REFERENCES`は、どのロールにも付けない。
- 内部用の関数（トリガー関数・`create_profile`・`normalize_nickname`等）は`service_role`だけが実行できる。
- 今後`public`スキーマに作るオブジェクトは、`anon`・`authenticated`へ自動では公開されない。
- 権限の一覧は`supabase/tests/api_privileges_test.sql`で固定している。新しいテーブル・ビュー・関数を追加するときは、必要な権限を同じ移行で付け、このテストの期待値も更新する。公開しすぎるとテストが落ちる。
- 認証済みの利用者向けの`posts`は全列を読める（ブロック・通報で投稿者を指定するため）。

### 12. 投稿・コメントのAPI（Issue #13・2026-10-14）

- 書き込みは`service_role`専用のDB関数（`create_post`・`update_post_body`・`delete_post`・`set_post_reaction_mode`・`create_comment`・`update_comment_body`・`delete_comment`）で、権限・受付状態・ブロック・利用停止の確認と保存を1トランザクションにまとめる。anon・authenticatedには実行権限を付けない。
- コメント作成は投稿行を`for share`、反応モード変更は`for update`でロックし、受付終了とコメント保存が同時に走っても、受付終了が確定した後に新規コメントが保存されない（`supabase/tests/concurrency/run.sh`で検証。ロックを外すと再現する）。
- `idempotency_keys`（service_role専用）で作成系の再送を重複させない。利用者ごと・エンドポイントごと、24時間を過ぎたものは次回の呼び出しで削除する。
- 本文の文字数はDBでは緩い上限（投稿7,000・コメント3,500コードポイント）で、1,000・500文字（絵文字等は1文字）の検証はEdge Functionで行う。
- `public_posts`は投稿者のニックネーム・アイコンを結合し（owner権限の`post_author_profile()`経由）、利用者IDを出さない。`member_comments`（ログイン必須）はコメント一覧用。`public_profiles`は自分自身と公開中の投稿・コメントの投稿者に限り、未ログインには公開しない。

### 13. ブロック・非表示・ミュートの適用（Issue #14・2026-10-14）

- 設定（`blocks`・`hidden_items`・`muted_topics`・`muted_words`）は、本人限定のRLSで直接操作する（CLAUDE.mdの方針どおり）。
- 取得は`member_posts`（詳細）・`feed_posts`（一覧・検索）・`member_comments`・`notifications`のRLSで除外する。いずれも`security_invoker`のビューで、`auth.uid()`の設定だけを参照する。未ログインには公開しない。
- `muted_words`は`normalized_word`（NFKC＋小文字化）をトリガーで設定し、利用者ごとに一意。上限（100件）は利用者単位のロックで同時登録でも超えない。

### 14. 共感・保存（Issue #15・2026-10-14）

- 共感の書き込みは`set_reaction()`・`remove_reaction()`（service_role専用）に一本化した。`reactions`は、authenticatedが自分の行を参照するだけで、INSERT・UPDATE・DELETEの権限とポリシーを持たない（CLAUDE.mdの「本人限定RLSで直接操作してよい」一覧から外れた）。
- 保存は、本人のRLS（参照・追加・削除）で直接操作する。追加は可視な投稿（`member_posts`）に限る。`saved_post_list`ビューは、見える投稿だけを保存日時つきで返す。

### 15. 投稿の検索（Issue #16・2026-10-14）

- `posts.body`にPGroongaのインデックス（`posts_body_pgroonga`）を持つ。拡張はextensionsスキーマ。
- 検索は`search_posts()`（`security definer`、anon・authenticatedが実行可）。公開条件を関数の中に明示し、`member_posts`・`feed_posts`と同じ意味にしている（`post_search_test.sql`で一致を検証）。利用者の入力はSQLに埋め込まず、パラメータで渡す。
