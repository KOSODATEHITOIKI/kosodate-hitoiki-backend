# バックエンド設計

更新日：2026-09-29。要件は決定済み、実現方式は明記したものを除き設計案。

## 1. 担当範囲と構成

**決定済み**：Flutterアプリとバックエンドを別リポジトリで管理し、バックエンドにSupabaseを採用する。無料プランで開始し、必要になった段階で有料プランを検討する。

| 領域 | このリポジトリで扱う内容 |
|---|---|
| DB | テーブル、制約、インデックス、マイグレーション |
| 権限 | RLS、公開可能な項目、本人・運営者の操作範囲 |
| 認証 | メール・Google・Appleログインに必要なバックエンド設定 |
| サーバー処理 | 送信前チェック、投稿等の保存、退会処理、運営操作 |
| 通知 | 通知データ、通知設定、プッシュ配信処理 |
| 運用 | 通報対処記録、バックアップ、復旧手順 |

管理画面のUI実装先は未決定。本リポジトリでは管理画面が利用する権限・データ操作を扱う。

**設計案**：通常の読み取りはRLSで保護したDBアクセスを基本とし、外部APIを利用する処理はEdge Functions、複数データを不可分に更新する処理はDB関数・トランザクションに集約する。具体的なAPI名・引数・レスポンスは今後定義する。

## 2. 閲覧と操作の境界

以下は決定済み要件。画面上の非表示だけで済ませず、DB・APIからも取得や操作を拒否する。

| 対象 | 権限・条件 |
|---|---|
| 公開状態の投稿本文・コメント件数・投稿本文検索 | 未ログインでも利用可 |
| コメント・返信本文、プロフィール本文 | ログイン必須 |
| 投稿上のニックネーム | 公開表示。プロフィール本文とは権限を分ける |
| 投稿・コメントの作成 | ログイン必須。受付状態・ブロック等も確認 |
| 投稿・コメント・プロフィールの編集 | 本人のみ。文章は編集時も送信前チェック |
| 共感の件数 | 投稿者のみ閲覧可 |
| 保存一覧 | 保存した本人のみ。他者へ保存数・通知を公開しない |
| ミュート・ブロック設定 | 本人が管理。相手へ通知しない |
| 通報・対処記録 | 相手へ通報者情報を公開しない。運営者の参照範囲は詳細設計で定義 |
| 管理操作 | 運営者のみ。二段階認証必須 |

**決定済み**：共感はログイン必須。共感ボタンと定型文は1つのリアクション機能に統一し、運営の定型文から1投稿1人1つ選ぶ（変更・取消可能）。コメント受付終了後も利用可能。

**設計案**：公開投稿の取得経路に認証情報・プロフィール本文・共感件数・通報情報を含めない。ビューやDB関数でもRLSを意図せず迂回しないように権限を検証する。特権キーはアプリへ配布しない。

## 3. 投稿・コメント

**決定済み**：投稿種類は「ぐち」「相談」「コツ／体験談」。話題は任意で1つ。一覧は新着順のみ。

| 項目 | 制約 |
|---|---|
| 投稿本文 | 1,000文字まで |
| コメント・返信 | 500文字まで。返信は1段階のみ |
| ニックネーム | 2〜12文字、重複不可、30日に1回変更可 |
| 自己紹介 | 任意、100文字まで |

空入力の拒否は受入条件案。

**決定済み**：ニックネームは全角・半角、英字の大文字・小文字、前後の空白の違いを同一視して重複判定する。絵文字等も見た目の1文字として数え、2〜12文字とする（具体的なUnicode処理は#9で定義）。変更前の名前は30日間他人が使用できないが、本人は再利用できる（変更自体は30日に1回の制限に従う）。

反応モードとコメント受付状態は別の概念として管理する。

| 状態 | 新規自由コメント・返信 | 既存コメント |
|---|---|---|
| ただ聞いてほしい（初期値） | 不可 | 残してログイン後に閲覧可 |
| 話を聞きたい・受付中 | 条件を満たすログイン利用者が送信可 | ログイン後に閲覧可 |
| 話を聞きたい・受付終了 | 不可 | 残してログイン後に閲覧可 |

投稿者は「ただ聞いてほしい」から「話を聞きたい」へ変更でき、受付終了後も再開できる。離席による自動終了は行わない。受付終了後も共感ボタンは継続する。

**決定済み**：「話を聞きたい」から「ただ聞いてほしい」への逆方向変更も可能。既存コメントは残し、新規の自由コメント・返信のみ停止する。受付終了後も投稿者本人は既存コメントを編集できる（編集時も送信前チェックを実施）。親コメントを削除した場合は本文を「削除済み」に置き換えて表示し、返信は残す（実データの削除方法・退会時の全体削除との整合は#9で設計する）。コメントは古い順に表示し、返信は対象の親コメントの下に表示する。返信を投稿すると返信先コメントの投稿者へ通知する（同一人物への重複通知・自分自身への通知は行わない）。

**設計案**：保存時点で受付状態を確認し、受付終了前に開いた画面からの送信も拒否する。受付変更とコメント保存が同時に起きても制約を守れるトランザクションを設計する。

### 投稿・コメントの実装方針（Issue #13）

**決定済み（2026-10-14）**：投稿1,000文字・コメント500文字は、ニックネームと同じく絵文字等を見た目の1文字（書記素）として数える（DBは緩い上限だけを持ち、厳密な検証はEdge Functionで行う）。投稿の編集は本文のみ（種類・話題・反応モードは別の操作）。投稿一覧のニックネーム表示は、`public_posts`にニックネーム・アイコンを結合した列を持たせ、利用者IDは公開しない。

**設計案**：

- 本文は前後の空白を除いて1文字以上（空白のみの投稿・コメントは不可）。
- 書き込みは`security definer`ではなく`service_role`専用のDB関数（RPC）で1トランザクションにまとめる。権限・受付状態・ブロック・利用停止の確認と保存を同じトランザクションで行い、受付終了とコメント保存が競合しても新規コメントを保存しない（投稿行のロックで直列化）。
- 作成系は`Idempotency-Key`で再送を重複させない（保存期間24時間、利用者ごと）。
- 「編集済み」は専用の`edited_at`で判定する（`updated_at`は反応モード変更でも変わるため使わない）。本文が実際に変わったときだけ設定する。
- 投稿削除は関連するコメント・返信・共感・保存・通知を削除し、本人だけの非表示（`hidden_items`）の残骸も消す。通報の記録は保持期間（1年）まで残す。
- 公開プロフィール（`public_profiles`）は、自分自身と、公開中の投稿・コメントの投稿者に限る（投稿のない登録者の一覧を公開しない）。
- 利用停止中は、新規作成に加えて既存の投稿・コメントの編集も不可にする（安全側。未決事項に記録）。削除済み・一時非表示のコメントへの新規返信は不可にする（同じく未決事項）。

### ブロック・非表示・ミュートの適用（Issue #14）

**決定済み**：ブロック・自分だけの非表示は、画面だけでなくDB・APIの取得でも除外する。ブロックされた相手には通知せず、事実も参照できない。公開投稿は、ブロックされた側からも見える。

**設計案**：投稿・コメント・通知の取得は、ログイン済み用のビュー（`member_posts`・`feed_posts`・`member_comments`）とRLSで除外する。ミュートは一覧・検索（`feed_posts`）にだけ適用し、詳細（ID指定）には適用しない（通知からの参照などを妨げないため）。言葉ミュートは全角・半角と大小文字を区別しない部分一致で、投稿の本文にだけ適用する。ミュートする言葉は100件・100文字までを暫定の上限とする（未決事項）。

## 4. 送信前チェック

**決定済み**：投稿・コメント・返信・ニックネーム・自己紹介を対象とし、編集時にも実施する。禁止語リストとOpenAI Moderation APIで開始する方針。日本語の愚痴と攻撃の区別は公開前に実例で検証する。

他者への攻撃・差別・名前や個人情報は送信を防ぐ一方、自分のつらさを吐き出す表現は制限しない。自分や子どもへの危害をほのめかす書き込みは止めず、本人にのみ相談先を案内する。イニシャルや公人・作品名は機械的に禁止しない。

**設計案**：チェックを経た本文と実際に保存する本文が一致する経路を設ける。クライアントがチェック結果を自己申告したり、DBへ直接書き込んだりして迂回できないようにする。外部API呼び出し後、保存直前にも権限と受付状態を再確認する。

**決定済み**：外部API（OpenAI Moderation API）が障害等で応答しない場合は、保存をブロックして利用者に再試行を促す（安全側に倒し、チェックを経ない投稿の保存を許可しない）。

**設計案（Issue #11で実装）**：正規表現（電話番号・メール・郵便番号・住所）と禁止語をローカルで先に判定し、該当しなければModeration APIで判定する。境界域は確認表示（`confirm`）、明確な攻撃・差別・脅迫は`reject`、危害のほのめかしは投稿を許可して本人にだけ相談先を案内する。閾値・評価例・判定結果は[送信前チェック評価](送信前チェック評価.md)に記録する。

未決定：判定の閾値の確定値（初期値は未調整）、確認表示を無視して送った場合の扱い、相談先の内容、誤判定への対応窓口。Moderation APIだけで全要件が満たせることは未検証（APIの実測は未取得）。

## 5. ブロック・通報・運営

**決定済み**：AがBをブロックすると、AにはBの投稿・コメント・返信を表示せず、BはAの投稿・コメントへのコメント・返信・共感ができない。投稿本文は公開されるため、BからAの投稿を完全に隠す仕様ではない。

異なる3人から通報された投稿・コメントは自動で一時非表示にする。同一の通報者・同一の対象への通報は1件として扱い、件数を増やさない。運営は再表示・削除・警告・利用停止を行い、削除時は本人に理由を通知する。対処操作を自動記録する。

**決定済み**：運営が再表示した後は、対応済みの通報を再集計しない。再表示後に寄せられる新たな通報は運営が個別に確認し、自動非表示は繰り返さない。投稿が一時非表示の場合はコメント・返信も一般利用者から隠し、新規コメント・共感の投稿を停止する。削除済み・一時非表示のコメントは、公開するコメント件数に含めない。

利用停止は段階的に運用する：初回7日間→再発時30日間→さらに再発した場合は無期限。停止中は本人による新規投稿・コメント・共感・通報を禁止するが、既存の投稿・コメントは公開を維持する（第三者への影響を避けるため）。悪質性の判定基準や異議申立ての窓口・対応時間は未決定（[未決事項](未決事項.md)参照）。

**設計案**：通報の一意制約とトランザクションで同時通報を扱う。一時非表示は一覧・検索・詳細など各取得経路で適用する。

## 6. 通知・削除

**決定済み**：自由コメントは投稿者へ個別通知、共感はまとめて通知する。返信は返信先コメントの投稿者へ通知する（3節参照）。利用者は通知を停止できる。集約頻度・配信サービスは未決定。

投稿削除時はコメント・返信・共感も削除する。退会時は投稿・コメント・プロフィール・保存投稿を削除し、ニックネームは30日間他者が再利用できないようにする（本人は再利用可）。

**決定済み**：通報対処記録は1年、バックアップは30日を保持期間として削除する。退会前の確認表示・退会の取消期間の要否は未決定（[未決事項](未決事項.md)参照）。

## 7. 登録・投稿の制限

**決定済み**：登録直後は投稿・コメントの件数に軽いレート制限を設ける。具体的な日数・件数、および新規登録の一時停止の要否は固定値でなく設定テーブルで運営がトグル・変更できるようにする（コード変更・再デプロイなしで調整可能にする）。

**設計案**：レート制限・新規登録停止の設定値を保持するテーブルを設け、認証・投稿・コメントの各保存処理で参照する。設定変更の権限は運営者のみに限定する。
