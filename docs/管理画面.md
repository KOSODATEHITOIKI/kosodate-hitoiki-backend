# 管理画面

更新日：2026-10-23。運営者向けの管理画面（通報の対処・運営設定・記録）の構成、守っていること、公開の手順をまとめる。**決定済み**：実装先・配信先・アドレス・運営者の人数（下記）。**設計案**：Cloudflare Accessの設定と、本番への切り替え手順。

## 1. 決定済みの事項

| 項目 | 内容 |
|---|---|
| 実装先 | 別リポジトリ [kosodate-hitoiki-admin](https://github.com/KOSODATEHITOIKI/kosodate-hitoiki-admin)（非公開）。Flutterアプリには運営の画面を作らない |
| 形 | スマホでも使える小さなWeb画面。ビルドなしの静的ページ（外部の部品を使わない） |
| 配信 | Cloudflare Pages |
| アドレス | `admin.kosodate-hitoiki.com` |
| 運営者の人数 | 当面1人（開発者本人） |
| 使えるのは | 運営者のみ。二段階認証（TOTP）を済ませたセッション（`aal2`）だけ。権限の判定はバックエンドが行う（[運営の二段階認証](運営の二段階認証.md)） |

## 2. できること

| 画面 | 内容 | 呼ぶAPI |
|---|---|---|
| ログイン | メール・パスワード → 認証アプリの6桁のコード | Supabase Auth（`/auth/v1/...`） |
| 通報の一覧 | 未対応の通報がある対象（一時非表示中を先に） | `admin_report_queue`（ビュー） |
| 対処 | 本文、通報（理由・補足）、これまでの対処を見て、再表示・削除・警告・利用停止・相談先の案内を実行 | `POST /moderation/actions` |
| 運営設定 | 新規登録の停止・再開、登録直後の投稿頻度制限 | `GET`/`PUT /moderation/settings` |
| 記録 | 最近の運営の対処 | `moderation_actions` |

API契約は[API契約](API契約.md)の運営の節を参照。画面のために新しいAPI・権限は追加していない。

## 3. 守っていること（情報漏えいの対策）

- **外部のスクリプトを読み込まない**。部品・解析・広告を入れない。供給網経由の混入を避けるため、ビルドもしない。
- **厳しいCSP**（`public/_headers`）：`default-src 'none'`、`script-src 'self'`、`style-src 'self'`、`connect-src`は接続先のAPIだけ、`frame-ancestors 'none'`。インラインのスクリプト・スタイルは使わない。
- **利用者が書いた文字はテキストとして表示**する。`innerHTML`などの禁止をテストで確かめている。
- **通報者のIDは取得しない**（画面にも出さない）。
- **セッションは`sessionStorage`だけ**（タブを閉じると消える）。15分操作がなければ自動でログアウトする。
- **操作は確認ダイアログを経る**。削除・警告・利用停止は理由の入力が必須で、サーバーに記録される。
- **公開キー以外の鍵を置かない**（`secret`・`service_role`は置かない）。テストが確かめる。
- 検索エンジンに載せない（`noindex`、`robots.txt`、`X-Robots-Tag`）。`Cache-Control: no-store`。

## 4. 公開の手順（手作業）

1. **Cloudflare Pages**：Workers & Pages → Create → Pages → Connect to Git で`kosodate-hitoiki-admin`を選ぶ。公開前は`develop`をproductionブランチにする。ビルドコマンドは空、出力ディレクトリは`public`。
2. **カスタムドメイン**：`admin.kosodate-hitoiki.com`を追加する（DNSは同じCloudflare内）。
3. **Cloudflare Access**（設計案）：運営者のメールだけを許可するポリシーを作り、ワンタイムコードで入口を絞る。`*.pages.dev`とプレビューにも同じポリシーをかける。**支払い方法の登録を求められたら止めて、判断する**（無料の範囲かは公式で未確認）。
4. 開いてログインし、スマホで通報の一覧が出ることを確かめる。

Accessは「入口を一つ増やす」ためのもので、画面の権限は、Accessが無くても[運営の二段階認証](運営の二段階認証.md)の仕組みで守られる（二重の守り）。

## 5. 本番への切り替え

公開前は、devに接続する。リリースのときに、次の2か所を**同じ接続先にそろえて**差し替える（`tests`が一致を確かめる）。

- `public/js/config.js`の`ENVIRONMENTS`（接続先と公開キー）
- `public/_headers`の`connect-src`

本番の運営者アカウント（二段階認証の登録を含む）は、[運営の二段階認証](運営の二段階認証.md)の手順で作る。
